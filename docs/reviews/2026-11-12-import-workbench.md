## 第三轮（新审查代理，复审已发布的 v0.2.0）

1 个 P1、2 个 P2，均已修复（v0.2.1）：

- P1-1：以只读方式打开一个 WAL 库时，若当时没有别的连接，SQLite 仍会新建 `-wal`/`-shm`（本机已复现）。以 root 运行时这两个文件归 root、权限 0644，工作台此后写库会报 readonly，导致无法在工作台删除配对。第三轮先用 immutable 打开来修，第四轮推翻了这个修法（见下）；最终修法是以 root 运行时在子进程里以数据库属主的身份只读打开。
- P2-1：安装收到 INT/TERM/HUP 信号时，EXIT trap 看到的 `$?` 为 0，没有恢复导入前的配置（已复现）。修法：EXIT trap 改为无条件恢复（备份只在服务已用新配置运行后才清空），并加 `trap 'exit 130' INT TERM HUP`。新增安装测试：在配置检查期间发 TERM，确认配置已恢复。把 trap 临时改回旧写法后这条测试失败，红绿对照成立。
- P2-2：以下三类限制会让整次导入失败，而不是只跳过越限的那个配对：请求预算、配对数上限、主账户 API 钱包与别的配对子账户相同。修法：先校验现有配置；每个候选配对和已接受的配对合并后试校验，失败只跳过它，并提示可用 `--pairs` 分批迁移。预算报错补上「加两成余量为 X」，与实际比较的数值一致。

P3 已修复：
- 配置里的 `adl` 与页面不同时写一行日志，不发飞书，避免每次启动都告警。
- 单独以 root 运行时，写出的文件沿用被替换文件的属主。
- 名称中的控制字符和格式字符不再输出。
- 无法解析的配对行会计数提示；用 `--pairs` 点名这类配对时，报错里注明原因。
- `restore_import` 某个文件失败时不中断，继续恢复其余文件，结束时报告失败的文件。
- 去掉测试里无意义的正则分支。

P3 已登记，待实测：
- 分批迁移时工作台和本服务共用主账户的签名钱包，写入 plan.md §6。

P3 未改：
- 测试里的 `1e3` 不是工作台会写出的值，但它测的是「本服务不接受的设置只跳过该配对」，保留。
- systemctl 分支仍只能在服务器上验证。

## 第四轮（新审查代理，只看第三轮修复）

第三轮的 P1-1 修法被推翻，问题均已修复：

- P1（chown 跟随符号链接）：关库后对新冒出的旁路文件执行 chown/chmod 时会跟随符号链接。工作台账户一旦被攻破，可以借此让 root 改掉任意文件的属主。
- P2-1（immutable 读）：工作台每做一次操作就开一次连接、用完就关，最后一个连接关闭时会删掉 `-wal`，所以「没有 `-wal`」不等于工作台已停。immutable 不加锁，读的同时工作台检查点会改写主文件，审查代理复现了 `database disk image is malformed`。
  - 修法：以 root 运行时用 `spawnSync` 起子进程，uid/gid 取数据库属主（libuv 会清空附加组），环境变量为空，只读打开并正常加锁，只把两张表的 data 列以 JSON 传回。immutable 和 chown 兜底都删掉了。
  - 测试：`readerIdentity` 的取值；运行中能读到未检查点的记录；读完后的旁路文件归库的属主；缺表时报读取失败。
  - 以 root 切换身份的那条路径只能在服务器上验证。
- P2-2：启动与健康检查期间收到信号时，配置文件被改回去了，但服务仍在用导入后的配置运行。修法：`systemctl` 执行前把信号处理改为只记下 `interrupted=1`，由健康检查结果走现有的成功或失败分支（第五轮又做了加固，见下）。
- P3（均已修复）：
  - EXIT trap 第一句先忽略信号，避免恢复中途被二次信号打断。
  - 逐对试校验不再重复推导签名。
  - 现有配置没有配对、校验失败时，提示检查现有 config.json 的其它字段。
  - main.ts 中只用于提示的 ADL 记录读取失败时不影响启动。

## 第五轮（新审查代理，只看第四轮修复）

无 P0/P1。2 个 P2 均已修复：

- P2-1：进入中断模式后，trap 和失败分支里的 `log` 只要写失败（SSH 断开、`| tee` 的 tee 被 Ctrl-C 杀掉），就会触发 `set -e` 或 SIGPIPE，使脚本中途退出。服务正在启动时配置却被改了回去，或者回退做到一半就停了。修法：`log` 不再失败；启动窗口内忽略 SIGPIPE，窗口结束后恢复。
- P2-2：终端 Ctrl-C 会发给整个前台进程组，健康检查里的 `sleep 5` 当场结束，5 秒稳定观察被跳过，服务可能被提前判为健康。修法：新增 `steady` 包装（子 shell 先忽略 INT/TERM/HUP 再 exec，忽略状态跨 exec 保留），健康检查里的 sleep、systemctl show，以及启动窗口内全部 systemctl、journalctl 都改走它。本机已实测：设有 INT 处理函数时，对进程组发 SIGINT，`steady sleep 2` 睡满 2 秒，不包的 sleep 当场结束。

P3 已修复：
- 健康检查一通过就清空备份，后面再有任何失败都不会把配置改回去。
- 导入子进程不再继承安装锁 fd 9。
- 数据库是符号链接或非普通文件时拒绝读取；root 运行时，若库文件归 root 而所在目录归其他账户，同样拒绝。
- 读取失败的报错先过滤控制字符、截断到 200 字，并注明是以哪个 uid 读取的。
- 现有密钥文件先完整校验一次，报错指明是它的问题。之后试校验和按钱包匹配账户都用规范化后的条目，签名只推导一次。
- 「可用 --pairs 分批迁移」只在超出预算的报错后附加。
- 子进程参数在库路径前加 `--`。
- 更正第四轮记录中不准确的表述。

## 第六轮（新审查代理，只看第五轮修复）

无 P0/P1/P2。3 个 P3：

- 启动窗口内取时间戳用的 `date` 可能被 Ctrl-C 打断，触发 `set -e` 退出。已改为 bash 内建的 `printf -v marker '%(%s)T' -1`，不再起子进程。
- 回退分支中的 `switch_to`、`write_unit` 没有忽略信号。已放进 `( trap '' INT TERM HUP; … )` 子 shell 执行；这两个函数不改动 shell 变量。
- 已登记、未修：`steady` 的子 shell 在 fork 之后、`trap ''` 生效之前，还有一个微秒级的窗口。TERM/HUP 恰好落在这里时，一次健康检查读数可能为空，正常运行的服务会被误判失败，按失败处理并回退，最终状态仍一致。

经核查无问题的项：`steady` 在 `set -e` 下的返回码；SIGPIPE 忽略的影响范围；去掉最后一次完整校验后，各项检查仍全部覆盖；`known` 回滚完整；`--` 之后的 argv；新增测试的断言有效。
