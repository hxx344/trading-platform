# 代码审查标准与流程

本文件规定单次改动合并前如何定级、审查和留痕。文档里出现的 R1/R2/R3、P0–P3、D1–D7 都以这里为准。具体经验条目见 [LESSONS.md](../LESSONS.md)，每批的审查结果见 [reviews/](reviews/)。

本文件由工作台（project-aggregation，`9e7d4c8`）的 `docs/code-review-standard.md`、`code-review-checklist.md`、`code-review-process.md` 精简合并而来，去掉了只属于工作台的内容（Python 与 Next.js 模块、特权更新器、提交门禁脚本、多客户端入口、各等级的首轮审查时限、度量与审查轮次硬上限）。

## 1. 适用范围

| 改动类型 | 审查方式 |
| --- | --- |
| `src/`、`web/`、`deploy/`、`scripts/`、`probes/`、`test/`、配置与依赖、CI 工作流 | 完整审查，按第 2 节分级 |
| 纯文档（`docs/`、`*.md`） | 轻量核对：结论与代码一致、引用路径存在、不复制其他文件的规则正文 |
| 生成物（`dist/`、`web/dist/`） | 不提交，不审 |

## 2. 改动分级

按风险分级，不按行数。分级存疑时按高一级处理。定级决定审查深度，不决定要不要审。

| 等级 | 判定 | 本仓库的典型范围 | 最低要求 |
| --- | --- | --- | --- |
| **R3 高风险** | 出错会直接造成资金、权限或不可逆后果 | 下单、平仓、划转、ADL、杠杆与保证金；凭据与鉴权；`install.sh`、root 导入助手、部署激活与回滚；主库与各模块状态库的结构与迁移；配置格式中影响资金的字段；唯一写者边界 | 独立审查（高风险档，范围大时按后端、页面分两路）+ 修复后复核 + 失败场景测试 + 回滚版本 |
| **R2 中风险** | 出错会静默产生错误数据或不可用 | 行情与持仓读取、缓存与失效、调度与恢复、通知、只读采集及其独立库（如 `monitor.sqlite`）里只加不改的表、页面重排、构建与依赖升级 | 自审 + 一路独立只读审查 + 相关测试 + 回滚版本 |
| **R1 低风险** | 影响局限于展示或文案 | 样式、文案、纯展示组件、补充单测、文档 | 自审；影响代码时做相应检查，纯文档核对引用与结论 |

R3 改动先写清四件事再改代码：要改变的用户可见行为、影响面、失败时会怎样与怎么回滚、本次不做而需要单独登记的事项。新模块按 [AGENTS.md](../AGENTS.md) 的要求写进对应模块文档。

## 3. 严重级别

| 级别 | 定义 | 处置 |
| --- | --- | --- |
| **P0 阻断** | 会造成资金、持仓、订单错误，凭据泄露，越权操作，数据损坏，或使部署无法回滚 | 必须修复，禁止合并 |
| **P1 阻断** | 会静默产生过期或错配数据、真实用户入口不可用、恢复无界，或声称验证但未执行 | 必须修复，禁止合并 |
| **P2 应修** | 不改变当前结果，但会放大后续缺陷：重复逻辑、错误处理不足、未测量的性能退化、测试缺口 | 可合并，须同批修复或登记到审查记录 |
| **P3 建议** | 命名、注释、可读性、局部风格 | 不阻塞，作者可拒绝 |

P0、P1 必须给出「触发条件 + 代码位置 + 后果」。给不出复现路径的判断只能标为**待核实**，不按 P1 阻塞，也不写成已修复。

## 4. 审查维度

按顺序看，先语义后细节。括号内是 [LESSONS.md](../LESSONS.md) 里的对应条目。

### D1 结果正确性与数据语义

- 单位、精度、计价币种是否与目标一致？
- 标的、合约、账户的身份是否全程可区分，有没有在某一层被合并？
- 分子与分母是否描述同一口径？
- 时间窗口、分页、全历史读取是否覆盖声称的范围？满页、空页、不前进时是否当作不完整而不是完整？（L093）
- 成交或事件之后，读取到的现场是否**证明**已反映该事件，而不是“应该已经反映”？（L054）

### D2 状态、缓存与时效

- 缓存的读取语义是否等于当前计算语义？失效条件覆盖哪些更新？
- 调度周期是否被误当成数据有效期？调度是否扣除了请求耗时？（L049）
- 写操作是否让之前发出的读取失效？迟到的旧响应会不会覆盖写入结果？（L089）
- 配置迁移或导入时，同值写入会不会覆盖页面上已保存的选择？

### D3 失败路径与有界恢复

- 每个网络、磁盘、外部调用：超时、重试次数、退避、总时限是否明确且有界？
- 结果未知的请求有没有出口：有界查询后转入当前状态核验，而不是无限查询或永久阻塞？（L039、L092）
- 最终判定用的账户现场，是不是在最后一次异步查询之后读的？（L091）
- 减险单是否有独立的重试上限，是否误用了开仓的发送条件？（L084）
- 多步资金流程重试时，是否从落盘的进度续做，而不是重做已完成的步骤？（L095）
- 断开、重连、卸载、切页时，定时器与订阅是否清理，会不会重复启动轮询链？

### D4 安全、权限与资金边界

- 特权操作的输入是否只来自可信来源，而不是请求体或页面可改字段？
- 凭据、token、账户标识是否可能进入日志、错误信息、响应或页面打包产物？
- 新增接口是否都经过与同类接口一致的登录检查，包括只读接口？
- 失败是否默认拒绝，而不是默认放行？
- 读取别的进程的 SQLite 或做备份导入时，是否保留了秘密材料、未决状态与原服务可用性？（L063）

### D5 真实入口与交付路径

- 改动是否在用户实际使用的入口上验证过，而不是只在替身后端或开发服务器上？没验证的写进「未运行」。
- 安装包实际包含的内容是否与提交一致？`install.sh` 的改动是否覆盖全新安装、升级、回退版本？
- 回退到上一版本是否要改配置或数据？写进文档的回滚版本是否正确？

### D6 验证与证据

- 新增或修改的测试是否覆盖失败场景，而不只是成功路径？
- 作者是否实际运行了相关检查？引用已有测试不等于运行过。
- 页面与后端对同一金额、条件的语法是否一致，并有测试同时覆盖两侧？

### D7 变更卫生

- 一个改动是否只做一件事？重构与行为变更是否分开？
- 是否有调试残留、`.only`、临时开关、注释掉的代码、被放宽的断言？
- 同类路径是否一起处理，或明确登记？
- 模块文档、README 与实际行为是否一致？没有把未修的问题写成已修。

## 5. 自审清单

提交前按适用类别过一遍，不适用的类别整类跳过。勾选不等于已验证，涉及运行的部分要写出命令与结果。

**通用**

- [ ] 改动只做一件事，没有夹带无关文件
- [ ] `pnpm check`、相关测试已运行；改页面时 `pnpm build:web` 并在替身后端上用浏览器看过 1280 与 390 宽度
- [ ] 新增分支有失败场景测试，或说明为何不需要
- [ ] 没有调试残留、`.only`、被放宽的断言
- [ ] 文档与实际行为一致；回滚版本已写明（R2 以上）

**数据与状态**

- [ ] 单位、精度、计价币种一致；分页与时间窗口覆盖声称的范围（L093）
- [ ] 事件后的读取能证明已反映该事件（L054）
- [ ] 调度周期没有被当作数据有效期（L049）；写操作使在途读取失效（L089）

**失败路径**

- [ ] 超时、重试次数、总时限有界；结果未知的请求有出口（L039、L092）
- [ ] 最终判定前重新读取现场（L091）；减险单有独立上限（L084）；多步流程按落盘进度续做（L095）
- [ ] 卸载、切页、停服时定时器与订阅已清理

**安全与资金边界（R3 必查）**

- [ ] 特权操作输入只来自可信来源；失败默认拒绝
- [ ] 凭据不进入日志、错误信息、响应、页面打包产物
- [ ] 新增接口在登录检查之后，含只读接口
- [ ] 有独立审查记录与回滚版本

**交付**

- [ ] 新模块的启用与数据迁移做进了「从工作台导入」（见 [module-import.md](module-import.md)）
- [ ] 数据库改动可重复执行，旧版本读新库不出错，或写明回退步骤
- [ ] 真实账户、真实交易所上没验证的内容写进「未运行」或 [live-results.md](live-results.md) 的待实测

## 6. 流程

```
定级 → （R3）变更前对齐 → 实现与自审 → 独立审查 → 修复与复核 → 合并 → 发布
```

### 提交信息

代码、配置和测试提交按下面的格式留痕，纯文档提交只写做了什么。

```text
feat(monitor): 一句中文摘要

更新说明：一到三句面向用户的变化与影响，简体中文，不写实现细节

风险等级：R2（一句话理由）

已运行：pnpm check；pnpm test（861 通过）；替身后端浏览器 1280 / 390
未运行：真实 Binance 接口（本机地区限制）
待确认：服务器上首次回补耗时

（署名行由提交工具写入，保留且只出现一次）
```

「更新说明：」和它的内容写在同一行：发布工作流（`.github/workflows/release.yml`）按行提取以它开头的行，作为发布说明。合并提交里的更新说明不会被提取。

「已运行」只写实际执行过的命令与结果。复用修复前的结果时写明是修复前的。

### 独立审查

- 作者代理不能同时充当唯一审查者。审查者只读：不改代码、不提交、不合并。
- 审查者的上下文与作者隔离：只给仓库、固定的差异范围、本文件与待核查重点，不给作者的结论与自评。
- 多轮审查每轮新开审查者，只给本轮差异、已关闭问题清单和待核查重点。
- 涉及鉴权、凭据处理或交易执行边界的改动，另按安全审查的要求进行。
- 审查顺序：意图与范围（有没有该一起改而没改的同类路径）→ D1、D2 → D3 → D4、D5 → D6、D7 → 可读性。
- 审查者不因风格偏好定级，不把未核实的猜测写成结论，不要求文案改动补复述实现的测试。

意见格式，一条一议。同一根因的多个位置合并为一条，列出全部受影响位置。

```text
[P1] src/monitor/funding.ts:120
问题：
触发：
后果：
依据：L0xx 或本文件条目
建议：
```

在 Claude Code 里可以用 `/review <范围>` 发起，命令定义在 `.claude/commands/review.md`。

### 修复与复核

- 作者逐条回应：修复、拒绝并说明理由、或转为 P2 登记。不因意见与己见不同就静默忽略。
- 复核只看增量差异与关联面，不重开全量审查。
- 第 3 轮仍有 P0/P1 时先停下来重新对齐方案，对齐后再继续审查，不在原方案上继续打补丁。
- 修复引入新逻辑时按新改动重新定级。

### 合并门槛

1. 按影响范围选择的类型检查、相关测试与必要 CI 通过。
2. P0、P1 为 0；P2 已修复或登记在审查记录里。
3. R2 以上有独立审查记录；R3 另有回滚版本。
4. 证据齐全：运行了什么、结果如何、什么没运行及原因。
5. 模块文档已回填实际做法。
6. 改动范围与描述一致，没有夹带。

### 审查记录

每批写一份 `docs/reviews/<日期>-<批次>.md`，包含：日期、范围（提交区间与文件）、等级与审查方式、回滚版本、审查结论（已核实的内容、按级别列出的问题与处理）、已运行、未运行。写法照 [reviews/](reviews/) 里已有的记录。

合并后才发现的 P0/P1 记为**逃逸缺陷**：在对应审查记录里补记，并判断是否值得写进 [LESSONS.md](../LESSONS.md) 或给第 5 节补一项。清单只因真实逃逸而增加。

### 热修

只用于线上已出现的 P0。改动最小化，只修该缺陷；合并后 24 小时内补一次完整审查并写审查记录；补审发现的遗留问题按正常流程处理。
