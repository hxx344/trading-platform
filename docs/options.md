## 2 业务规则（与工作台 `modules/greeks/app` 提交 160e932 一致，下单顺序除外）

- 合约：Bybit `category=option`、`baseCoin=BTC`；BTC 指数取 `linear` `BTCUSDT` 的 `indexPrice`。
- 选腿：只看未来最近的周日（UTC）到期；卖出 Call、卖出 Put 各取 |delta| 最接近 0.45 的行权价，须卖 Put 行权价 < 卖 Call 行权价；铁鹰再买入行权价在卖腿外侧、|delta| 最接近 0.10 的 Call / Put。四腿（宽跨两腿）数量相同。
- 实盘开仓只允许周五（UTC），且到期日须是本周日。
- 风险：铁鹰最大亏损 = 最宽一翼 × 数量 − 按执行价算的权利金，须 ≤ `maxRiskUsd`，保证金估算也须 ≤ `maxRiskUsd`；卖出宽跨亏损无上限，按 Bybit 官方期权下单初始保证金公式算的卖腿保证金（含缓冲）须 ≤ `maxMarginUsd`。执行中按见过的最差价格持续预留，超出即停止该任务后续下单与改价。
- 净价：开仓计划默认“最低净收入” = 按被动价（买腿买一、卖腿卖一）估算的净权利金扣手续费；平仓默认“最高净支出”。确认时可改。手续费估算 = min(费率 × 指数, 封顶比例 × 价格) × 数量。执行中按各腿最差价格预留，突破即停止后续下单与改价。
- 下单：每腿一张 GTC 限价单（买腿挂买一、卖腿挂卖一，按最小价格步长四舍五入），盘口变化就改价，每 1 s 看一次；`orderTimeoutSeconds`（默认 600）后撤单并核对（最多 5 次、间隔 1 s）。订单编号 `tpo-<任务>-<序号>`，平仓 `tpo-close-<任务>-<序号>`，平仓单 reduceOnly。订单状态同时查实时与历史两处，两处都查不到算“未知”，不当作已撤。
- 下单顺序（与工作台不同，2026-11-13 用户决定）：先买后卖。开仓先下两条买翼，全部成交后才下卖腿；平仓先买回卖腿，全部成交后才卖出买翼。买入腿没有全部成交（停止、净价或风险超限、行情过期、超时、结果未知）时卖出腿不下单，任务按已成交情况记为部分成交、已停止或失败（买入腿结果未知时为待核对），铁鹰任何时候都不会留下无保护的卖出，最坏是多出已付权利金的买翼。两轮各有 `orderTimeoutSeconds`，总执行时间最长约为两倍；卖腿不再检查开仓日期，周五临近午夜确认时卖腿可能在周六挂出（到期日仍是本周日）。卖出宽跨开仓只有卖腿、平仓只有买腿，各一轮。工作台四腿同时挂单。
- 定时开仓（G2a，同工作台 `scheduler.py`）：开关打开时每 5 s 检查一次；在周五（UTC）`openHourUtc:openMinuteUtc` 起 `openWindowSeconds` 秒的窗口内、本 ISO 周还没开过，就按当前设置（策略、每腿数量、上限）生成开仓计划并以请求编号 `scheduled-<ISO 周>` 提交，最低净收入用计划默认值。受理时再查一次窗口，下第一单前再查一次，过了窗口不下单。每周最多受理一次（受理即记入本周，结果是部分成交或失败也不再补开）。窗口内被拒（有未结束任务或订单、跟踪中的策略、行情过期、超出上限等）每 5 s 重试，同一原因只记一次日志；窗口结束仍未开出时发一条飞书“本周定时开仓未执行”。开关默认取 `config.json` 的 `options.autoOpen`（缺省关）；页面上切换后存进 `options.sqlite`，此后以页面为准，改 `config.json` 不再起作用：紧急关闭在页面上操作，页面打不开时从 `config.json` 删掉整个 `options` 停用期权模块。关闭定时不会停止已受理的定时任务（在“组合执行”里停止）。在窗口内打开开关，下一次检查（约 5 s）就会开仓，确认框会提示。打开前页面弹出确认，列出时间、策略、数量、上限与 IOC 设置。
- IOC 兜底（G2a，同工作台 `orders.py` market=True，`options.marketFallback`，缺省关）：只用于没停止的开仓任务，某腿超时撤单后结果是部分成交或未成交、且任务没有因净价或风险超限停止时，等 0.8 s 不撤单再读一次原单，剩余数量符合交易所最小 / 最大数量与步长，就发一张 IOC 限价单：买入挂卖一向下取整到价格步长、卖出挂买一向上取整。下单前按这个价格做净价与风险预留，超出就不发。只发一次，不重发；发出后读回，仍未结束则撤单再读。订单编号 `tpo-ioc-<任务>-<序号>`。与“先买后卖”的关系：IOC 在各腿所在的那一轮里执行，买入腿含 IOC 全部成交才下卖腿。注意：默认的最低净收入是按被动价估算的，对手价 IOC 通常会突破它而被拦下；要让 IOC 真正生效，需在手动确认时调低最低净收入。定时开仓用的是默认值，所以定时任务的 IOC 一般不会发出（与工作台相同）。
- 收益（G2b，同工作台 `performance.py` 的 `build_performance` 与 `performance.js`，提交 0c5a219，差异见各条）：
  - 台账：本服务自己订单（`tpo-` 编号）的每笔成交按成交编号存入 `options.sqlite` 的 `executions` 表，不设上限（状态文档里的“近期成交”仍只留 100 条）。来源：任务执行中每 3 s 与结束时读各订单成交（同 G1）；收益循环每 15 s 找订单记录里成交数量多于台账的订单补读（每轮最多 10 笔，每笔 25 s 上限，只补读已结束、7 天内的订单，失败后约 5 分钟再读；Bybit 按订单编号只能查到最近 7 天，更早的缺口一直显示“开仓成交历史尚未补齐”）。工作台按账户、按周游标同步全部成交并靠编号前缀归属；本服务只交易自己的订单，按订单补读，不读无关成交。v0.14.0 首次启动时把状态文档里已有的近期成交写入台账。
  - 归属：成交按订单记录（编号 → 任务）归到任务。开仓任务就是一次组合开仓；平仓任务的成交按先进先出匹配到它的开仓任务的同合约反向剩余仓位，开仓手续费按匹配数量分摊；找不到开仓任务或数量对不上的平仓记为“未可靠归属”或待核对。开仓任务结束且一笔没成交（失败 / 已停止）的不算组合开仓（工作台会把它列为待核对）。
  - 交割与平仓：退役跟踪腿时，平仓历史证据额外保存 `totalPnl`、`totalOpenFee`、`totalCloseFee`、`deliveryFee`、`avgEntryPrice`。有证据时组合收益以交易所平仓 / 交割记录为准（已含手续费），替代按成交匹配的收益，不叠加。v0.14.0 之前退役的证据没有这些字段，显示“交割或平仓收益待核对”、不纳入统计。
  - 纳入综合统计：只有已结束、无待核对问题、平仓历史证明各腿都在到期时间（到期日 08:00 UTC）及之后结算、只有一个到期日的组合；有提前平仓（含部分减仓，或证据里平仓手续费不为 0）的整组不纳入。按结算币种（`-USDT` 合约为 USDT，其余 USDC）分别统计累计净收益、胜率、采样最大回撤。
  - 采样：收益循环每 15 s 一次，持仓中的组合在到期前、没有待核对问题、最近一次读到的持仓不超过 60 s、且每条剩余腿在持仓里数量一致并只属于这一组时，距上一点满 60 s 就记一点盯市盈亏（已实现 + 按本组成本算的浮动盈亏 − 剩余仓位分摊的开仓手续费），存 `samples` 表。读不到持仓或有问题时不记，不补造；相邻两点超过 180 s 在图上断开。组合结束后以结束净收益作为最后一点，结束之后的采样不用。间隔固定 60 s（工作台 `PERFORMANCE_SAMPLE_SECONDS` 的默认值），不做配置、不导入。
  - 接口返回的点数：每组采样约 300 点、综合曲线约 1500 点，超出时按时间等分、每段保留最高与最低点，另加首尾、缺口两侧与结束点（工作台全部返回）；总收益、胜率与回撤用全部采样计算。每 15 s 的采样判断不带历史采样重算，开销不随采样增长。
- 交易所拒绝码按接口白名单判定（同工作台 `bybit.py`）；其他错误码、超时、5xx 都算“结果未知”，只能靠核对订单解决，不重发。
- 任务状态：进行中 accepted / running / stopping / recovering / recovery_needed；结束 completed / partial / stopped / failed。有未结束的订单或任务时不接受新计划。重启时进行中的任务改为 recovering 并请求停止，由对账循环撤单核对后结束。
- 跟踪策略：开仓成交累加到 `symbol|side` 数量，平仓成交扣减；平仓计划只平跟踪数量（不超过交易所持仓）。持仓里看不到某腿时，查交易所平仓历史（每次 7 天窗口，最多回溯 180 天），数量够了且再次读持仓仍看不到，才把该腿退役；全部退役则策略结束。
- 组合询价（G2c，同工作台 `rfq.py` 与 `app.js` 的 `renderRfq`，提交 2f0593d，差异见各条）：
  - 同一时间只有一笔询价，只用于开仓。按执行台当前的策略与每腿数量生成本周结构，创建前与开仓一样检查跟踪策略、风险上限、到期日；对象为 `/v5/rfq/config` 列出的全部做市商（最多 `maxLP` 家），铁鹰有交易所组合名时用组合名，否则 `custom`。询价关联号前缀 `tporfq`。
  - 每次写（创建、执行报价、取消）先把记录存成“结果待核对”再发送；交易所明确拒绝（`rejected` / `not-sent`）才按未发生处理，其余一律待核对，由每 3 s 的核对循环读实时与历史询价结算。创建后 2 分钟仍查不到的询价按未创建处理。核对循环开始读取后发生了本地写，这一轮读到的结果整体丢弃。
  - 询价没结束前（含等待报价）拦下所有开仓、平仓与定时开仓；询价自己的执行与取消不受此限。终态是已成交（且已转成开仓任务）、已取消、已过期、失败；已选报价的询价还须等到执行结果确定。
  - 执行报价前重新读一次报价并刷新行情，逐项核对：询价仍在等待报价且未选报价、询价与报价都还剩至少 2 s、报价恰好覆盖询价各腿且数量一致、价格为正、合约未变、到期日规则、按报价价格重算的组合风险不超上限；随后记下组合保证金基线，再核一遍才发送。同一报价重复执行返回已有结果。被明确拒绝（含询价专属拒绝码，见 `client.ts` 的 `TRADE_REFUSALS`）或应答为失败时回到等待报价、清掉选择，并恢复这次执行前的风险与组合保证金基线；工作台把应答失败直接记为终态，这里改为回到等待报价，真实状态由核对循环读交易所确定（失败的含义尚待实测）。服务正在停止时不发送。
  - 成交且 `/v5/rfq/trade-list` 的各腿与询价一致时，转成一笔已完成的开仓任务：任务 `planId` 为 `rfq:<询价号>`，每腿一条已结束的委托记录（`kind: 'rfq'`，订单号取自成交列表），跟踪数量按腿记入，之后的平仓、退役、收益与普通开仓相同；成交明细按订单号读取（大宗成交没有本服务的关联号），在台账里归到对应委托记录。成交列表按腿核对合约、数量、结果码与订单号；方向不比较（成交列表报的是本方还是报价方方向尚待实测）。询价已成交即说明已存的结构成交了（工作台只凭这一点跟踪）：成交列表还没到、对不上或读取失败时保持拦截、继续核对；从本服务首次看到已成交起（重启后重新计时）超过 2 分钟，按已存结构转成开仓任务（订单号留空、价格取报价，读不到成交明细，收益页该组待核对），记下原因并只发一次飞书，须人工核对成交明细。转任务时若已有其它跟踪中的策略（只有人工改动才可能出现），不覆盖原跟踪，询价按已结束处理并发一次飞书，须人工核对这笔持仓；核对前先关闭定时开仓（原策略平掉后不再有跟踪拦着开新仓）。
  - 报价只在内存，不落库；页面显示的报价净额、链净额差（卖出对比 Bid1、买入对比 Ask1）与预估手续费由服务按开仓时的费率口径算出。
  - 飞书：询价开仓成交一条；选中的报价没有成交（取消、过期、失败）一条；按询价结构兜底跟踪或因已有跟踪策略未接管时一条。
  - 长期锁定（交易所一直查不到已选报价或取消的询价）的最后手段：先在 Bybit 核对这笔询价确实没有成交或已手工处理，再停服务，执行 `sqlite3 <数据目录>/options.sqlite "UPDATE state SET json = json_set(json, '$.rfq', json('null')) WHERE id = 1"` 清掉询价记录后启动；已成交的持仓不会因此被跟踪。
- 唯一写者：工作台与本服务不协调。切换前须在工作台关闭自动开仓、处理完所有订单 / 任务 / RFQ 并平掉或接受跟踪策略后再导入（导入时检查）。本服务和原油模块可以使用同一个 Bybit 账户（期权与 USDT 永续互不影响），但工作台期权模块此后不能再用该账户下期权单。

## 3 架构

- 代码：`src/options/`（`client.ts` 期权客户端，`market.ts` 期权链，`strategy.ts` 选腿、预算与风险，`account.ts` 持仓 / Greeks / 账户健康，`orders.ts` 跟价下单与核对，`engine.ts` 计划 / 任务 / 对账 / 跟踪策略，`store.ts` 状态库），服务接线 `src/service/options.ts`、`options-config.ts`。
- 状态：单独的 `options.sqlite`，一行 JSON 状态文档（版本 1，带账户 UID；G2a 加 `schedule`：页面开关、本周已开、最近一次被拒原因与飞书提醒周，旧文档读入时补默认值），G2c 加 `rfq`：唯一一笔询价的记录，旧文档读入时为空；每次变更整体写入（WAL + synchronous=FULL），对应工作台原子写的 `engine_state.json`。G2b 在同一库加两张表：`executions`（成交台账，按成交编号）与 `samples`（收益采样，按组合与时间，只追加），状态文档版本与字段不变。主库不迁移，回退时不受影响。状态文档损坏或 UID 不符时拒绝启动。
- 配置 `config.json` 新增可选 `options`：`{ accountId, limits: { maxRiskUsd, maxMarginUsd }, legQty?, strategyMode?, marginMode?, orderTimeoutSeconds?, feeRate?, marginBufferPct?, autoOpen?, openHourUtc?, openMinuteUtc?, openWindowSeconds?, marketFallback? }`（缺省同工作台：1、iron_condor、REGULAR_MARGIN、600、0.0003、0.10、false、21、0、60、false；`openWindowSeconds` 1–300）；密钥 `secrets.json` 新增 `bybitOptions: { apiKey, apiSecret }`。`pairs`、`oil`、`options` 至少有一个。
- 启动：配置了 `options` 时取进程锁 `pa-options/bybit/<UID>`，读 `query-api` 检查密钥（读写、绑定 IP、只开合约交易 / 期权交易 / 统一账户衍生品，钱包、现货等都关闭）、统一账户、UID 与配置一致（30 s 上限），失败拒绝启动（安装时自动回退旧版本）。
- 循环：期权链每 10 s（单次 10 s 超时、失败保留上次结果并记日志）；定时开仓每 5 s（G2a）；对账每 15 s（核对未结束订单 → 结束已恢复的任务 → 同步持仓与退役）；账户健康每 15 s；收益每 15 s（补读成交、采样，G2b）；询价核对每 3 s（读询价状态、报价与成交列表，G2c）。
- 外部调用：每个 HTTP 请求 10 s 超时；只读请求不重试（下一轮再读），签名写请求只在时间戳被拒（10002，证明未执行）时同步时钟后重发一次。
- 结果未知的订单：对账撤单后读实时与历史订单。下单应答丢失、从未拿到订单号，发出已超过 2 分钟（Bybit 接收窗口 5 s）且不到 6 天（历史订单默认只查最近 7 天）、每次读取都明确查无此单时，按未下单（成交 0）结算；有订单号的始终保持未知、转人工。订单编号前缀为 `tpo-`（工作台为 `ic-`），回退后工作台不会把本服务的成交认成自己的。
- 接口（须登录，未配置 `options` 时 404）：

  - `GET /api/options/preview?quantity=&mode=`（策略预览）
  - `GET /api/options/state`（任务、订单、跟踪策略、持仓与 Greeks、账户健康、对账状态、近期成交、参数）
  - `POST /api/options/plans`、`POST /api/options/tasks`、`POST /api/options/tasks/<任务>/stop`
  - `POST /api/options/auto-open`（`{ enabled: boolean }`，G2a；状态里的 `schedule` 给出开关、来源、时间、下次时间、窗口状态与本周未执行原因）
  - `GET /api/options/performance`（G2b：各组合收益与采样、按币种的综合曲线与统计、未归属平仓数、采样间隔、台账条数与最早成交时间、最近一次补读或采样错误）
  - `GET /api/options/rfq`（G2c：询价记录与状态名、是否结束、排序后的报价及与盘口的对比、能否新建及原因、行情新鲜度）
  - `POST /api/options/rfq`（`{ requestId, confirmLive: true, quantity?, mode? }`，请求编号幂等）
  - `POST /api/options/rfq/execute`（`{ rfqId, quoteId, confirmLive: true }`）
  - `POST /api/options/rfq/cancel`（`{ rfqId }`）。
- 飞书：任务确认、结束、转人工各一条（同一任务同一状态只发一次，经 `notify.sqlite` 发件箱）；定时任务标题写“期权定时开仓任务”；本周定时开仓未执行一条（每周最多一次）。
- 页面：顶部“期权”标签只在 `GET /api/options/state` 有应答时出现。
  - 排版照工作台 `modules/greeks/app/static/index.html`：执行台（指标行、期权链、策略腿与到期收益图、Greeks 汇总、执行控制、账户保证金健康度）、持仓（持仓、近期成交）、组合执行（进行中 / 历史任务卡片）。
  - 样式复制自工作台 `modules/greeks/app/static/style.css`，加 `.options-desk ` 前缀。
  - 确认对话框：腿、金额、净价限制输入、风险说明、勾选确认后提交；请求编号沿用 RequestIds。
  - 表单到请求的转换在不依赖 DOM 的 `web/src/options-form.ts`。
  - G2a：执行控制底部“计划开仓”一行显示定时状态与下次时间，带打开 / 关闭按钮；顶部提示条显示“定时开仓 周五 HH:MM UTC”或“只手动开仓”（打开 IOC 时加“+ IOC 兜底”），本周未执行时显示原因；委托明细里 IOC 单标“IOC”，定时任务卡片标“定时”。

## 4 切换与回退

切换：

1. 工作台期权模块关闭自动开仓：在 `DATA_DIR/modules/greeks/.env`（或 `/etc/project-aggregation.env`）写 `AUTO_OPEN=false` 后在工作台重启该模块（工作台页面没有这个开关；导入会读运行中模块进程的环境核对）。等跟踪策略到期或平掉，确认没有挂单、任务和 RFQ。
2. 本服务页面导入期权（或手写配置）→ 服务重启并通过启动检查。
3. 先看行情、预览和账户健康度正常；周五用最小数量（0.01）走一次开仓，周日到期或手动平仓。

回退：`sudo bash install.sh --version v0.10.1`。回退前在页面关闭定时开仓（页面开关存在 `options.sqlite`，以后重新导入同一账户会沿用），确认没有进行中的期权任务和未结束订单；旧版本不认识 `options` 与 `bybitOptions`，回退前须从 `config.json` 删掉 `options`、从 `secrets.json` 删掉 `bybitOptions`。`options.sqlite` 留在数据目录，旧版本不读。

从 v0.13.0（G2a）回退到 v0.11.0 / v0.12.0（保留期权模块）：先在页面关闭定时开仓、确认没有进行中的任务，再从 `config.json` 的 `options` 删掉 `autoOpen`、`openHourUtc`、`openMinuteUtc`、`openWindowSeconds`、`marketFallback`（旧版本按白名单读字段，多出字段会拒绝启动；工作台设置过开仓时间或开着 IOC 兜底时，v0.13.0 的导入会写入对应字段），然后 `sudo bash install.sh --version v0.12.0`。状态文档里多出的 `schedule` 与 IOC 订单记录旧版本会忽略。

从 v0.17.0（G2c）回退到 v0.16.0：先在“组合询价”页确认没有未结束的询价（标签上不显示“进行中”；已成交但还没转成跟踪的也算未结束），再 `sudo bash install.sh --version v0.16.0`，配置不用改。旧版本保留但不读状态文档里的 `rfq`，也不会拦下交易；询价成交转成的开仓组合照常跟踪与平仓，但旧版本按关联号读不到这类大宗成交，收益页该组显示待核对，再升级后按订单号补读（7 天内）。

从 v0.14.0（G2b）回退到 v0.13.0：直接 `sudo bash install.sh --version v0.13.0`。`executions`、`samples` 两张表旧版本不读；状态文档没有新字段，平仓证据里多出的金额字段旧版本不看。回退期间不采样，再升级后曲线在这段时间断开；回退期间的成交再升级后按订单补读（7 天内）；回退期间退役的腿没有金额字段，那一组显示待核对。回退后若要回到工作台交易，工作台的 `engine_state.json` 不含本服务期间的任务与跟踪策略，须先确认账户无期权持仓。
