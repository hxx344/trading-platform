# Ondo 批量撤单与最优价提前撤单审查

2026-11-19，R3（实盘撤单路径）。范围是 `c2f751f` 之上的一批改动：`src/vendor/ondo/{client,mm,quote,stream}.mjs` 及其类型声明、`web/src/ondo/OndoPage.tsx` 的一条状态文案、`docs/ondo.md`、`test/ondo/{client,mm,stream}.test.mjs`。回退版本为 v0.65.0，操作见 [Ondo 模块文档](../ondo.md) 文首 v0.66.0 小节。

改动内容：同一回合发起的撤单合并为一次 `DELETE /v1/perps/orders/batch`（最多 20 张）；同一市场到期的撤单同时发出；实盘另开一条不登录的 `topOfBooksPerps` 连接，比上一帧深度盘口新的买一卖一可提前触发保护撤单，该侧随后等到不早于该时刻的深度盘口（最多 1.5 秒）才重新挂。最优价不参与挂价和保护金额，观察模式不使用。

审查方式：两轮独立只读审查，每轮新开审查者，只给差异范围、接口规范出处与审查标准。首轮看实现完成时的工作区差异，第二轮看修复后的完整差异并逐条核对首轮问题。

| 首轮问题 | 处理 |
| --- | --- |
| P1，批量请求收到非 4xx 的带码拒绝（如 HTTP 200 加 `order_already_fully_filled`）时，这个码被发给批内每张单，仍挂着的单会被当成已全部成交并停止跟踪 | 这类应答下每张单都按结果未知处理并停用批量；只有通过身份和终态核对的成功项、或失败项自带的错误码，才算某张单的明确结果 |
| P2，最优价连接在订阅确认后立即被断开时每秒重连，并不限次数地写事件 | 订阅稳定 10 秒后才清零退避并报告就绪，只有报告过就绪的连接断开才报告断开，每个会话最多记 20 条连接状态 |
| P2，测试没有覆盖真实客户端与挂单状态机的组合，以及时间戳重签、在途关闭、提前撤单被拒 | 补了真实客户端加替身交易所的集成测试（批量应答漏列一张单：先按订单号核对，之后才重新挂单，不重发），以及其余场景的测试 |
| P3，规范里不可撤状态码有两种拼写；任一市场停止交易会让整个会话停用批量 | 两种拼写和 `trading_disabled` 都按单项状态处理：逐笔重发，之后仍用批量 |
| P3，提前撤单的累计次数把未发出撤单的情况也算了进去 | 只在真正发出撤单时计数和记事件；未发出的单仍被标记，稍后照常撤 |
| P3，超前本机不超过 1.5 秒的最优价时间戳会让随后不超过 1.5 秒内的最优价被忽略 | 不改：后果只是少触发提前撤单，深度盘口的保护照常生效 |

## 增量复核

第二轮确认首轮各项已关闭，未发现 P0、P1、P2。复核逐一列出了请求层可能抛出的每种错误在批量路径中的去向，结论是只有两种情况会把一张单判为已撤或已成交：它列在成功项里并通过身份与终态核对，或它列在失败项里且该行自带错误码。复核另提两条建议，均已处理：HTTP 2xx 但没有错误码的批量应答现在也停用批量（此前只按结果未知处理，与文档不一致）；撤单仍在退避期的单不再计入提前撤单次数。这两处修改之后没有再做独立审查，只重跑了定向测试。
