# DEX 价差：把 Var / Lighter 做成通用双腿价差模块

**状态：D1–D3 已在 v0.88.0 一次实施（回滚版本 v0.87.0），D4 未做；v0.89.0 把 Lighter 与 Entropy 的盘口和 Entropy 的标记价、资金费改为 WebSocket（第 10.10 节，回滚版本 v0.88.0）；v0.90.0 拆成独立服务（第 11 节，回滚版本 v0.89.0）。** 2026-11-25 起草，同日实施。第 0–9 节是原方案，**实际做法以第 10 节为准**（与方案不同处在那里写明）。现有 Var / Lighter 模块的做法见 [varlighter.md](varlighter.md)，本文只写变的部分；没提到的规则（基线、时段、开平仓、风控顺序、回测不看未来等）沿用该文。

## 0 目标与结论

- 把「Var 对 Lighter（RH、主网）」推广成「任意两个场所的两条腿」：A 腿、B 腿各来自一个场所适配器，算法不再知道哪边是 Var。
- 第一个新场所是 **Entropy**（Hyperliquid HIP-3 的 `io` 市场）。
- 支持**自定义配对**：用户指定 A、B 两条腿（场所 + 代码）和合约乘数，经规格确认后启用。这样也能用上现在判为 `mismatch` 的标的（单位不同但可换算的）。
- 仍然**只做模拟盘**：只读公开行情（Var token 询价照旧），不下单，不碰执行器、划转、资金。下单连接器以后按场所适配器逐个接，不在本方案内。
- 模块身份不变：配置键 `varLighter`、页面 `#/varlighter`、接口 `/api/varlighter/*`、只读令牌范围与 MCP 工具名都沿用，只把页面标题改为「DEX 价差」。这样不用迁移配置、令牌和书签。

## 1 分步与定级

按 [code-review.md](code-review.md) 第 2 节，涉及模块状态库结构与迁移的定为 R3；分级存疑取高。每步单独发布，回滚版本都是该步发布前的上一版。

| 步 | 内容 | 定级 | 验收 |
| --- | --- | --- | --- |
| D1 | **只重构**：场所适配器接口、两腿样本表、两腿持仓与成交、配对键改为两腿；现有 Var↔RH、Var↔主网迁过来，行为不变 | R3 | 同一批样本，重构前后 `backtest.ts` 的成交、净盈亏逐笔相同；模拟盘持仓升级后继续跟踪 |
| D2 | **Entropy 适配器**：目录、一档行情流、盘口快照、按场所的手续费；自动配对 Var↔Entropy、Lighter↔Entropy | R2 | 替身行情测试；部署后实盘准备页 Entropy 采集正常、对齐样本入库 |
| D3 | **自定义配对**：页面增删配对、乘数、规格确认；采样节拍按配对 | R3（改参数存储格式） | 表单测试；乘数校验与 5% 规格核对；页面 1280 / 390 走查 |
| D4 | 按需接入其他场所（Aster、Hyperliquid 主站等，复用行情监控的适配器） | 每家 R2 | 同 D2 |

## 2 场所适配器（D1）

新目录 `src/varlighter/venues/`，每个场所一个文件，实现同一接口：

| 能力 | 说明 | Var | Lighter RH / 主网 | Entropy |
| --- | --- | --- | --- | --- |
| `catalog` | 标的目录：代码、资产类别、精度、最小数量与金额、标记价、手续费 | `metadata/stats` 的 listings | `orderBookDetails` | Hyperliquid `info {type:'meta', dex:'io'}` |
| `top` | 一档买卖价与时刻（按时刻保留历史，供对齐回看） | 每分钟公开报价（`base / 1k / 100k` 三档） | `market_stats/all` 行情流 | `wss://api.hyperliquid.xyz/ws` 订阅 `bbo`（+ `activeAssetCtx` 取标记价与资金费） |
| `depth` | 1k / 100k 美元冲击 | 报价自带档位 | `orderBookOrders` 每分钟快照 | `info {type:'l2Book'}` 每分钟快照 |
| `quote`（可选） | 按数量询价 | token 询价（`varquote.ts`，规则不变） | 无 | 无 |
| `cadence` | 本场所报价的自然节拍 | 60 秒、报价自带时刻 | 实时 | 实时 |
| `fee` | 每次成交的 taker 费率 | 0 | 0 | 按目录的 `deployerFeeScale`、`growthMode` 折算（同 `src/vendor/perpetual-additional-exchanges.mjs` 的算法） |

- 「对齐」的规则不变：样本时刻 `t` 取较慢一腿的报价时刻，另一腿取行情流在 `t` 之前最近的一档；判断时刻的一档（现在的 `rhBidRx`）推广为两腿各一个，实时腿才有。
- 判断时刻按腿取价（`targetSpread`）。有效且数量匹配的 Var 询价可用于对应数量，行情流腿用决策一档，公共档回退记录来源。
- 适配器只用公开接口和已有的 Var token，不读其他凭据。

## 3 两腿数据结构（D1）

### 3.1 配对键

- 新格式 `<场所>:<代码>|<场所>:<代码>`，A 在前，如 `var:AAPL|rh:AAPL`、`lighter:BTC|entropy:io:BTC`。
- 现有键 `rh:AAPL` 等价于 `var:AAPL|rh:AAPL`，`lighter:BTC` 等价于 `var:BTC|lighter:BTC`。迁移时改写参数、规格确认、冷却、持仓、成交里的键；接口仍接受旧键（映射到新键），旧的详情页地址照常打开。
- 方向名从 `var_rich` / `var_cheap` 改为 `a_rich` / `a_cheap`；页面按两腿的场所名写成「卖 Var 买 RH」这类全称。

### 3.2 存储

不在原表上改列，**在同一个 `varlighter.sqlite` 里新建表**，旧表不再写入：

- `leg_samples`：配对键 + `t` 主键；`regime`、`received_at`；A、B 两腿各一组列 `a_* / b_*`：`at`、`bid0`、`ask0`、`mark`、`funding`、`bid1k`、`ask1k`、`bid100k`、`ask100k`、`bid_rx`、`ask_rx`、`bid_tk`、`ask_tk`、`tk_at`（可空的按现有规则可空）；另加 `ratio`（该样本按的乘数，见第 4 节）。
- `leg_positions`、`leg_trades`：结构同现有 `paper_positions`、`paper_trades`（JSON 正文），正文里两腿按 A / B 存，带各腿费率。
- `events`、`state` 沿用；新的参数与配对定义存在 `state` 的新键（`pairs`、`params2`），旧键 `params` 保留不动。

**迁移**（启动时一次，带完成标记）：

- 样本：**不复制**。读取时把旧 `samples` 表按 `var_* → a_*`、`rh_* → b_*` 映射成同样的结构，与 `leg_samples` 按 `t` 拼接（以切换时刻为界，不会重复）。旧表照常按 14 天保留期清理，两周后自然清空，不占双份磁盘、不拖慢启动。
- 持仓、成交、冷却、参数、规格确认：行数少，复制并改写键与字段进新表 / 新键；旧表、旧键原样保留。
- 迁移在一个事务里完成；失败则不写完成标记、关库，本模块在这次运行里不可用（接口 503），不影响其他模块，下次启动重试。

### 3.3 回滚

- 回到 D1 发布前的版本（预计 v0.87.0）：旧版本只认旧表与旧键，读到的是**升级那一刻**的模拟持仓、成交和参数；升级后的新样本、新成交、新配对它看不到，旧 `samples` 表从升级时起的那段是空档。只是模拟盘，可接受；回滚后建议在页面清空模拟盘重新开始。
- 再次升级：完成标记已在，不重复迁移；回滚期间旧版本写进旧表的样本照常被拼接读到，但回滚期间旧版本产生的模拟持仓、成交不会再迁过来（发布说明里写明）。
- 只停模块不回退：`"varLighter": false`，不变。

## 4 自定义配对与乘数（D3）

- **自动配对**照旧：两个场所里同名（Entropy 去掉 `io:` 前缀；v0.91.0 起另认代码别名，见第 10.4 节）、两边标记价相差 ≤ 5% 的，按现有 `verified / review / mismatch` 规则生成。D2 起自动配对的场所组合：Var↔RH、Var↔主网、Var↔Entropy、主网↔Entropy、RH↔Entropy。哪些组合默认采集待用户确认（第 8 节）。
- **手动配对**：实盘准备页「配对管理」里填 A 腿（场所 + 代码）、B 腿（场所 + 代码）、乘数 `k`、备注。
  - 基差按 `A 价 ÷ (k × B 价) − 1` 算；两腿名义金额仍相等（各自按自己的价折算数量），`k` 只影响基差，不影响下单数量。
  - `k` 必须来自合约规格（例：某一边报价是「每 1 美元代表 10 亿美元市值」），填一次、不随行情拟合；改 `k` 视为新配对（旧样本的 `ratio` 不同，不混入基线）。
  - 保存时按当前标记价核对 `|A ÷ (k × B) − 1| ≤ 5%`，不满足拒绝；通过后仍是 `review`，要人工确认才能启用模拟盘。
  - 两条腿不能是同一场所同一代码；同一场所不同代码（如股票对 ETF）首版不支持。
  - 上限：手动配对最多 100 个；每个场所启用的配对数上限（10）不变，按配对涉及的每个场所分别计。
- **持仓冲突**：现在的「同一 Var 代码已在另一场所持仓」推广为：同一场所同一代码只能出现在一个有持仓的配对里（任一腿冲突都不开）。

## 5 采样节拍与统计口径（D3）

- 每个配对的节拍取两腿中较慢的一腿：含 Var 的仍是每分钟；两腿都实时（如主网↔Entropy）时，已启用或有持仓的配对默认每 15 秒一个样本，其余仍每分钟。
- 统计不能再假设「一个样本 = 一分钟」：`minSamples` 改为按覆盖时长（分钟）判断；AR(1) 半衰期、每天穿越次数、样本占比先按分钟重采样再算，否则不同节拍的配对不可比。回测与模拟盘同一口径。
- 容量要重估：现在约 210 个配对、每天约 30 万条样本、14 天约 0.85 GB。加上 Entropy 的自动配对、以及 15 秒节拍的已启用配对（每个场所最多 10 个，每个每天 5760 条），按配对数实测后写进第 7 节；数据目录预留按实测结果更新。

## 6 Entropy 细节（D2）

- 目录：`POST https://api.hyperliquid.xyz/info {type:'meta', dex:'io'}`，代码形如 `io:XXX`，抵押 USDC，资金费每小时。行情监控已用同一个目录与同一套订阅（[monitor.md](monitor.md)），本模块复用 `src/vendor/` 里的解析，不复制一份。
- 规格：`src/vendor/perpetual-additional-exchanges.mjs` 只把 SNDK、NBIS、GPRO、IONQ 认作「每股」合约；OAI、ANTH 是市值报价（1 美元代表 10 亿美元市值），其余是 Entropy 独立合约。所以 Entropy 的自动配对大多会落在 `review` 或 `mismatch`，**主要靠手动配对加乘数**。
- 手续费：不是 0。预期净利、下单预演的滑点保护、盈亏都要按两腿各自的费率扣；费率取不到（目录字段变化）时该配对不开仓。
- 请求额度：Hyperliquid 按出口 IP 限制 WebSocket 连接数、订阅数与 REST 权重，行情监控的 Hyperliquid / Entropy 采集用的是同一个 IP。实施前按 Hyperliquid 当时的文档核对限额，本模块只订阅 `io` 市场，盘口快照每分钟最多 10 个；超限时退避，不影响行情监控。
- 地区：开发机能连通（行情监控冒烟），部署机以实测为准。

- `/api/varlighter/*` 路径不变；应答里每行多出 `legs: [{ venue, venueName, symbol }, { … }]`，原有 `venue`、`symbol` 字段在 D1 仍给（含 Var 的配对填 B 腿场所与代码），D3 之后再评估删除。`samples` 接口的 `columns` 换成两腿列名。
- 新增 `POST settings` 的 `pairs` 字段（增、改乘数、删手动配对）；删除有持仓的配对返回 409。
- 只读 MCP 的 `varlighter_backtest` 与 `tools/varlighter/*`：本机缓存按格式版本分目录，格式变了重新拉取；同时能读旧缓存做对比。
- 页面（按 [frontend.md](frontend.md)《页面开发规则》，对照页面就是现有的 Var/Lighter 价差页，回滚版本同第 3.3 节）：
  - 页头每个采集中的场所一枚状态，场所列表来自适配器，不写死。
  - 总览的场所筛选改为「A 腿场所 / B 腿场所」；表格两列显示两条腿。
  - 详情、模拟盘按两腿显示价格与费率。
  - 实盘准备页新增「配对管理」（手动配对的增删、乘数、备注，规格确认沿用现有）。
  - 1280 与 390 宽度走查，表格在面板内横向滚动。

## 8 待用户确认（已定，见第 10.7 节）

1. 首版接入 Entropy 后，默认采集哪些场所组合（全部自动配对会让流量和样本量明显上升）；是否先只做 Var↔Entropy 与主网↔Entropy。
2. 两腿都实时的配对，启用后的采样节拍（默认 15 秒）是否合适。
3. Entropy 的手动配对清单：哪些标的、各自的乘数依据（合约规格页链接）。
4. 回滚时丢失升级后模拟盘记录（第 3.3 节）是否可接受。
5. 之后要接的其他场所与先后顺序。

## 9 本方案不做

- 任何场所的下单连接器、实盘开平仓；账户资金。
- 同一场所内不同代码的配对（股票对 ETF 等）。
- 三腿及以上组合。
- 资金费进净盈亏（沿用现状：只估算）。

## 10 实际做法（v0.88.0）

D1、D2、D3 合在 v0.88.0 一次发布，回滚版本 v0.87.0；定级 R3（库结构与迁移）。与第 0–9 节不同的地方逐条写在下面。

### 10.1 代码位置

- 没有新建 `src/varlighter/venues/`：场所差异集中在 `model.ts`（目录解析 `parseRhMarkets`、`parseEntropyMarkets`，组合 `COMBOS`、配对 `comboPairs`、`customPairInfo`，场所名）与 `feeds.ts`（`LighterStream`、`HyperliquidStream` 同一 `LiveStream` 接口，盘口快照 `fetchDepth`、`fetchEntropyDepth`）。Var 仍是每分钟轮询加可选 token 询价，不走行情流接口。
- 引擎（`engine.ts`）按场所各持一个运行时（行情流、目录、各腿的盘口快照）；只有被开着的组合或手动配对用到的场所才连行情流。
- 模块身份照第 0 节不变：配置键 `varLighter`、`#/varlighter`、`/api/varlighter/*`、MCP 工具名不变；页面与左侧栏标题改为「DEX 价差」。

### 10.2 配对键与方向

- 新键 `场所:代码|场所:代码[@乘数]`；Entropy 的代码**去掉 `io:` 前缀**（`entropy:NVDA`，不是方案里写的 `entropy:io:NVDA`），目录里的 `io:` 名只在请求 Hyperliquid 时用。
- 乘数 1 不写；否则写成十进制，10 位有效数字、最多 10 位小数（`formatRatio`），同一配对只有一种写法，`parsePairKey` 拒绝其他写法。两腿同场所的键拒绝。
- 旧键 `rh:X`、`lighter:X` 在接口、只读工具、本机回测与详情页地址里都按 `var:X|rh:X`、`var:X|lighter:X` 认（`upgradeKey`）。
- 方向 `a_rich`（卖 A 买 B）/ `a_cheap`；页面按两腿场所写成「卖 Var · 买 RH」。

### 10.3 存储与迁移

- 同一 `varlighter.sqlite` 新建 `leg_samples`、`leg_positions`、`leg_trades`；参数存 `state` 的 `settings2`，冷却存 `cooldown2`；旧表、旧键原样保留、不再写入。
- 样本不复制：读取时把旧 `samples` 按 `var_* → a_*`、`rh_* → b_*` 映射，与新表按时刻合并（`legacyKeyOf` 只对 Var 对 Lighter 两场所、同代码、乘数 1 的键有旧键）。旧表照 14 天保留期清理。
- 启动时 `migrateLegacy` 在一个事务里：持仓、成交改写键、方向与两腿字段（旧手续费 `varFeeBps`、`rhFeeBps` 记进各腿），旧参数经 `upgradeSettings` 换新键、新方向，原采集场所换成组合（原来采集 RH 的开 Var↔RH；采集主网的开 Var↔主网与主网↔Entropy；Var↔Entropy 总开），写完成标记 `legs_migrated`；失败整体回滚、关库，模块在这次运行里不可用（接口 503，日志写原因），下次启动重试。有内容迁移时记一条事件并写日志。
- 回滚到 v0.87.0：照第 3.3 节，升级后的样本、成交、参数改动旧版本看不到；再次升级不重复迁移，所以回滚期间在旧版本里改的参数、开平的模拟仓也不会带回新版本。

两腿表另存决策时刻 `decision_at`、两腿判断盘口时刻 `a_rx_at` / `b_rx_at`、询价原生数量 `*_tk_qty` 及本机应答时刻 `*_tk_received_at`。公开价来源仍在 `a_at` / `b_at`，询价来源仍在 `*_tk_at`，`received_at` 保留公开报价的接收时刻。采样口径 `capture_kind`、上述新增列均可空，样本导出格式 2 在既有列后追加，现有 A/B 缓存可以续拉。原始 `samples` 在同一升级事务中只给已证明没有判断盘口列的旧行登记 `legacy_aligned=1`。已升级过的库、回退后按旧列插入的样本都保留未知；回滚前后的各版本按列名读写。

### 10.4 自动配对、手动配对与校验

- 组合六个：Var↔RH、Var↔主网、Var↔Entropy、RH↔主网、RH↔Entropy、主网↔Entropy。默认开 Var↔RH、Var↔主网、Var↔Entropy、主网↔Entropy，RH↔主网与 RH↔Entropy 不开（第 10.7 节）。组合的自动配对是两场所同代码、乘数 1，规格按原 `verified / review / mismatch` 规则；不在已核对清单里的 Entropy 配对都是 `review`。
- **代码别名**（v0.91.0）：同一标的、同一计价单位、只是各场所代码不同的，登记在 `model.ts` 的 `SYMBOL_ALIASES`，自动配对把同组代码当作同代码（乘数 1，两个方向都认）。首个别名组是 `ANTHROPIC`（Lighter RH、主网）与 `ANTH`（Entropy），两边都按 10 亿股完全稀释估值报价（1 单位约 17.68 股）；Var 与 Lighter 的 `ANT` 是每股，不在这组，仍按同代码 `ANT` 配对。别名配对不进已核对表：价差超 5% 为 `mismatch`，否则 `review`，确认后才能启用；页面代码写「ANTHROPIC / ANTH」。`autoComboOf`（查重用）同样认别名，所以别名配对也不能再手动添加（`duplicate_pair`）。升级前已经存在、组合也早已开着的同键手动配对（只有加别名才会出现）不挡无关保存，配对表里自动配对优先，删掉后不能再按同键加回。回滚到 v0.90.1：别名配对消失，那条键上的启用参数与样本保留，改手动配对即可接上。新增别名组前先在两边公开目录核对计价单位与标记价。
- 手动配对最多 100 个，存于参数的 `pairs`（`{ a, b, ratio, kind, note }`），在实盘准备页「手动配对」增删。与方案不同：**保存时不因价格差拒绝**，按标记价算 `|A ÷ (k × B) − 1|`，超过 5% 标为 `mismatch`（不能启用），其余为 `review`（确认后才能启用）。这样目录暂时缺一腿时也能先存。
- 与开着的组合的自动配对同键时拒绝（`duplicate_pair`）：加手动配对与只开组合的保存都查；还启用着或有持仓的手动配对不能删（`pair_busy`，409）。
- 每个行情流场所启用或有持仓的配对的腿最多 10 条（`too_many`），按配对涉及的每个场所分别计；只挡让腿变多的保存，已经超额（升级前留下的）时无关的保存照常，取盘口快照时有持仓的配对排在前面、超出的不取。
- 规格校验只挡**这次新启用**的配对：已启用的配对规格降回 `review` 或 `mismatch` 时由开仓前的 `eligible` 挡住，不再让无关的保存（加手动配对、改全局参数）失败。
- 持仓冲突：同一场所同一代码只能出现在一个有持仓的配对里（`legBusy`）。

### 10.5 采样节拍与统计

- 含 Var 腿的配对仍跟每分钟的 Var 报价。目录与 Var 轮询在后台进行，不拖住行情流配对的采样；Entropy 目录在有组合或手动配对用到时每分钟取（带标记价与资金费），否则十分钟一次。两腿都是行情流的配对由 `sampleLive` 每 5 秒检查一次：已启用或有持仓的每 15 秒一个样本，其余每分钟一个（各留 1 秒余量）。v0.93.0 起分别是每 1 秒检查、5 秒、20 秒，见第 10.11 节。
- 与方案不同：没有把 `minSamples` 改成按时长、也没有在统计时重采样，而是**基线只每约一分钟收一个样本**（`LIVE_BASELINE_GAP_MS = 55 秒`），所以基线样本数、半衰期与穿越次数在不同节拍的配对之间可比；开平仓判断仍用每个样本。回测按同一规则（`bothLive` 的配对用同样的间隔）。

开仓按最终选用的每腿价格核验时效，采集等待计入决策时间。Var 在任一侧均按原生合约数量绑定询价，改名义金额的回测、持仓估值和平仓会按目标数量选询价或公共档。服务端和本机回测逐行读取决策口径；可证明的旧采样作历史估算，未知样本缺证时仍计入基线并阻止新开仓。已有持仓可按适用公共档位估值和平仓，降档、缺判断盘口等情况会标为估算。参数与来源字段见[策略和回测规则](varlighter.md#5-策略与模拟盘strategytsenginets)。

### 10.6 Entropy

- 目录：`POST /info {type:'metaAndAssetCtxs', dex:'io'}`，v0.88.0 有组合或手动配对用到 Entropy 时每分钟一次（带标记价、预言机价与资金费），否则十分钟一次，刚用到时立即取一次（v0.89.0 起一律十分钟，见第 10.10 节）；要求抵押资产为 USDC（`collateralToken` 0）、跳过已下架的。精度按 `szDecimals`，价格小数位 `6 − szDecimals`，最小金额按 10 USDC。
- 手续费：按 `deployerFeeScale` 与 `growthMode` 折算，基础 4.5 基点（同行情监控的算法）；字段不认识时为未知，该配对不开仓（实盘准备页「两腿手续费」一项提示），也可在全局参数里填手动值（四个场所各一个）。
- 市场编号取目录里的序号；目录变动后同一编号换了币种时，清掉该编号的旧一档；在途的 `l2Book` 确认按发出时的币种对回编号，不会记到新币种上。
- 行情流：`wss://api.hyperliquid.xyz/ws` 只订阅配对用到的市场的 `bbo`；bbo 只在最优价变化时推送，所以超过 50 秒没变化（或刚连上）的市场用 WebSocket `post` 发一次 `l2Book` 确认一档，每分钟最多 60 次；每 15 秒 `ping`，45 秒没消息断开重连。
- 盘口快照：v0.88.0 已启用或有持仓的配对每分钟一次 `l2Book`（REST），与 Lighter 同样每个场所最多 10 条腿（v0.89.0 起改为订阅，见第 10.10 节）。

### 10.11 行情流配对采样加快、总览勾选启用与自动配置（v0.93.0，R2，回滚版本 v0.92.1）

### 10.12 行情流配对的模拟盘按推送判断（v0.94.0，R2，回滚版本 v0.93.0）

用户要求：模拟盘也用行情流推送的价，不等固定间隔的样本。

- **做法**：行情流（`LighterStream`、`HyperliquidStream`）在某个市场的一档买卖价变化并记入历史后回调 `onTop(市场编号)`（只是标记价、资金费变化不回调）。引擎的 `onTop` 找出用到这条腿、两腿都是行情流、已启用或有持仓的配对，立即按两腿当前的一档建一个样本并用与定时采样相同的 `decide`、`tradeDecision`（复核、风控、自动配置）判断。有开平仓动作时把这一刻的样本写库并成交；没有动作或被挡住的不写库。定时采样（5 秒 / 20 秒）照旧，页面走势与绝大多数样本仍由它提供，推送判断只让开平仓更及时。推送时刻成交的样本和其他样本一样进库，也按约一分钟抽一个的规则可能计入基线；它与某条定时样本落在同一毫秒时这次不成交，等下一次推送或样本。入场、出场、止损与最长持有都会在推送时判断。
- **范围**：只对两腿都是行情流的配对（Lighter RH、主网、Entropy 之间）。含 Var 腿的配对不变：Var 没有带买卖价的推送，仍按每分钟的公开报价与 token 询价判断（对手腿早已取判断时刻的一档）。让 Var 配对也按推送判断需要在对手腿推送时即时向 Var 询价，会明显增加登录接口的请求数，未做。
- **状态**：`state` 接口的 `sources.push`（`checks` 判断次数、`trades` 成交次数、`lastTradeAt`、`lastBlocked` 最近一次被挡的配对、时刻与原因），实盘准备页「行情流配对」一行显示。
- **与回测的差别**：推送时刻成交的那条样本留在库里，用同样的参数、同样的持仓与冷却状态重放时会在这一条上成交。没有成交的推送不留样本：回测里看不到「推送时刻达到开仓条件但被挡住」的次数（定时样本上的仍有）；换一组参数回测时也拿不到推送时刻的价，只能在 5 秒样本上进出场，所以模拟盘的成绩可能好于回测。
- **负载**：判断在行情流的消息回调里同步进行。平时是内存计算（两条腿的一档、基线中位数、一次判断）；盘口冲击要把整本盘口排序，所以按推送判断时沿用 1 秒以内算过的快照（`PUSH_DEPTH_REUSE_MS`），每条腿每秒最多重算一次。出现开仓信号而被挡住（冷却、限额等）期间，每次推送都会读一次当日已实现盈亏（一条带索引的查询）；自动配置的配对每 10 分钟重算推荐值、基线跟踪器首次用到时的预热读库，也可能落在这个回调里。主网热门市场一档每秒可变多次，启用很多个这类配对时的 CPU 占用未实测。判断出错时丢弃该配对的基线跟踪器（下次重建），同一配对的出错日志每分钟最多一条。
- **回滚**：不改库表与参数，回到 v0.93.0 后只是开平仓回到按 5 秒样本判断。

### 10.13 持仓取档不随市值漂过分档线（v0.100.1，R2，回滚版本 v0.100.0）

起因：2026-11-26 模拟盘 29 笔净亏 33.34 美元，其中 4 笔止损亏 24.25 美元，多笔开仓几秒后就平掉。

- **根因**：持仓的平仓与止损按实际数量取价，档位按「数量 × 当前中间价」算（`model.ts` 的 `fillLeg()`）。默认名义金额 1000 美元正好在分档线上（≤ 1000 用 1k 档，否则 100k 档），开仓后价格涨一分钱，某条腿的市值变成 1000.03 美元，就按 10 万美元的盘口冲击算。Entropy 的 NVDA 100k 档冲击 30–50 基点、Lighter RH 的 ANTHROPIC 约 80 基点，1k 档只有 0–4 基点：浮亏一下子越过 60 基点的止损线，平仓价也按 100k 档成交。回测与模拟盘共用这段代码，回测同样偏低。
- **核实**：把 26 笔有样本的成交按这条规则逐笔重算，盈亏与记录全部吻合；同样的平仓时刻改按 1k 档是净赚 8.83 美元。同一批本机样本（基线窗口取 6 小时）重放，修复前五个配对合计 −18.90 美元（2 笔止损），修复后 +6.04 美元（没有止损）。
- **做法**：`sizeBucket(市值, 名义金额)`：市值在名义金额 ±20%（`BUCKET_DRIFT`）以内沿用名义金额的档位，超出才按市值取档。Var 精确询价后的对冲腿（数量来自询价的四位有效数字，折算后可能略过 1000）走同一条规则。按名义金额发现信号、开仓复核的取档不变。
- **没有改的**：分档仍只有 1k 与 100k 两档，名义金额 1001–99999 美元一律按 100k 档（偏保守）。名义金额略高于 1000 的仓，市值跌到 1000 以下时以前会改用 1k 档，现在 ±20% 以内保持 100k 档。
- **残留（已登记，未改）**：分档线没有消失，只是离默认值远了。名义金额约 834–1000 美元的仓，持有期内某条腿涨超 20% 且市值过 1000 美元时，那条腿仍一步跳到 100k 档，浮亏会多出几十基点，可能止损。保留这个上沿是因为价格大幅变化后的数量确实不同于开仓时（既有测试「按持仓实际单位估值」的口径）；要彻底去掉得在 1k 与 100k 之间按数量插值冲击，另行评估。「估算」标记的 `usd > 100_000` 是同类的线上阈值（名义金额 10 万美元的仓涨一分钱就标估算），只影响标记，不影响价格。
- **影响**：已有的成交记录不重算。自动配置的推荐参数只用中间价偏离与 1k 档往返成本，不受影响。
- **回滚**：不改库表与参数，回到 v0.100.0 即恢复按市值取档。
- **验证**：`test/varlighter.test.ts`「持仓取档」；审查记录 [reviews/2026-11-27-dexspread-size-bucket.md](reviews/2026-11-27-dexspread-size-bucket.md)。

### 10.14 模拟盘计入 Lighter 吃单延迟（v0.109.0，R3，回滚版本 v0.108.1）

定级 R3：改了实盘开仓意图的作废条件（`hasPaper`，见下文「平仓」），落在下单边界上。

起因：Lighter 主网与 RH 的标准账户吃单有 300 毫秒延迟（12.2），模拟盘却按判断那一刻的一档成交。模拟盘的信号多数来自一边报价没跟上，这 300 毫秒里对手往往已经跟上，模拟盘的成绩因此偏乐观。

- **做法**（`engine.ts` 的 `LIGHTER_TAKER_DELAY_MS`、`settleFills()`）：配对里有 Lighter 主网或 RH 的腿时，模拟成交分两步。
  - 开仓：判断时刻照旧按当时的价记仓、写开仓事件，实盘跟单也在这一刻发出（真实下单自己会经历吃单延迟，不再多等）。到判断后 300 毫秒，把 Lighter 腿的一档换成行情流历史里那一刻的一档，按同一套取价规则（盘口冲击沿用判断时刻的快照）重算两腿开仓价与入场价差，覆盖持仓并记一条「Lighter 吃单延迟 300 毫秒后成交：入场价差 x → y 基点」事件。数量不变（单子在判断时已按那时的价算好）。
  - 平仓：判断时刻只通知实盘跟单平仓，并且从这一刻起实盘查「模拟持仓是否还在」（`hasPaper`）就得到否，还没发出的实盘开仓意图随即作废、不下单；模拟持仓留到判断后 300 毫秒，按那一刻 Lighter 腿的一档结算，事件前注「Lighter 吃单延迟 300 毫秒后成交」。成交时刻、冷却、资金费估算仍按判断样本的时刻算。
  - Var 与 Entropy 的腿仍按判断时刻的价（Var 是询价或公开报价，Entropy 没有吃单延迟）。
  - 等待中的配对不再判断开平仓，也不按推送判断；样本照常写库。到点的处理在行情流每次推送、每轮样本入库前和引擎每秒一轮里做（每秒一轮里排在实盘推进之前），取价用 `topAt(到点时刻)`，处理晚了几百毫秒也取到的是到点那一刻的价。那一刻某条 Lighter 腿没有可用一档时沿用判断时刻的价并标为估算。
- **没有改的**：回测仍按样本时刻的价成交（样本里没有判断后 300 毫秒的一档）；模拟成交不设限价，延迟后价差变差多少都照样成交（实盘有限价保护，可能不成交）；付费账户的更短延迟没有做成参数。
- **停服与重启**：待处理的延迟成交只在内存里。正常停服时（主循环收尾、`close()`）在断开行情流之前全部结算：已到点的按到点那一刻的一档，没到点的按此刻的一档并标为估算，事件注「停服前提前结算」。进程被强杀时来不及结算：开仓保留判断时刻的价；平仓的模拟持仓还在而实盘已跟着平了，要等平仓条件再次满足才平，期间两边不一致；结算平仓那一刻写库失败同此（实盘仓已在平仓中，不会因此再开）。
- **等待中手动平仓**：平仓在等 300 毫秒时手动平仓，按最后一条样本、以「手动平仓」原因立即结算，原来的回归或止损原因与 300 毫秒后的价不再用；实盘那边只平已开的仓，不会多平一次。
- **影响**：已有的成交记录不重算。实盘跟单的开平仓时机不变。
- **回滚**：不改库表与参数，回到 v0.108.1 即恢复按判断时刻成交。
- **验证**：`test/varlighter.test.ts`「Lighter 吃单延迟」四条（两腿行情流的推送开平仓与等待中不判断、停服时提前结算并标估算、Var 对 RH 只改 RH 腿、平仓等待期间实盘开仓意图作废不下单）；到点缺一档的路径没有单独测试（行情流历史在判断时刻必有一档，要人为清掉历史才能触发）；既有引擎测试显式传 `takerDelayMs: 0` 保持原口径。审查记录 [reviews/2026-11-27-dexspread-taker-delay.md](reviews/2026-11-27-dexspread-taker-delay.md)。

## 11 独立服务（R3，v0.90.0，回滚版本 v0.89.0）

**状态：已实施，待发布。** 2026-11-26 用户决定：DEX 价差以后要接 Lighter、Entropy 的实盘，先把它从执行面拆成独立服务（S1），实盘在这个服务里另起一步做（S2，不在本方案内）。两步分开发布、分开审查。两轮方案审查的意见已全部改进正文，处理见 11.12、11.13；实施后审查的处理见 11.14 与 [reviews/2026-11-26-dexspread-service.md](reviews/2026-11-26-dexspread-service.md)。

### 11.1 为什么拆、拆成什么样

- 现状：DEX 价差跑在执行进程里（`src/service/main.ts` 的 `openVarLighter`、`varLighterLoop`），和 ASTER 划转、ADL、原油双腿同一进程。安装器按组件指纹决定重启谁（`deploy/component-digests.mjs`）：不在行情服务集合、也不是助手的文件一律算执行面，`src/varlighter/**` 因此在执行面指纹里，只改 DEX 价差也会有序重启执行面，ASTER 的划转与 ADL 停几十秒。按各版本改动的文件粗算，v0.64.1 到 v0.89.0 的 33 个改代码的版本里，有 6 个只因 DEX 价差重启执行面（v0.80.1、v0.81.0、v0.82.0、v0.83.0、v0.88.0、v0.89.0）。
- 同进程的另外两个代价：回测（`POST /api/varlighter/backtest`）是同步计算，跑在执行进程主线程上，长回测会拖住划转与 ADL 的循环；DEX 价差的崩溃会让执行面重启。
- 账户核对：Lighter、Entropy 账户只在 DEX 价差里出现，不和 ASTER、原油、期权、CrossEx、Ondo、MEV 共用，所以 S2 的实盘不需要与执行面的执行器、写入租约或账户锁交接。
- 做法参照行情服务（v0.67.0，[update.md](update.md)「公开行情独立更新」）：独立的 systemd 单元、系统账户、通信组和本机套接字；执行面作为客户端连它。**登录、会话、只读令牌、CSRF 检查和只读令牌的别名替换都留在执行面**，DEX 服务不对外监听、不认识会话。

| 组件 | 单元 | 账户 / 通信组 | 套接字 | 能访问 |
| --- | --- | --- | --- | --- |
| DEX 价差服务（新） | `trading-platform-dex.service` | `trading-platform-dex` / `trading-platform-dex-ipc` | `/run/trading-platform-dex/dex.sock`（0660，目录 2750） | 自己的状态目录 `/var/lib/trading-platform-dex`（0700，放 `varlighter.sqlite`）；公网：Var 公开接口与 token 询价、Lighter RH 与主网（REST、WebSocket）、Entropy（Hyperliquid `api.hyperliquid.xyz` 的 REST 与 WebSocket）。**不能**访问配置目录、执行面数据目录、导入与更新交接目录、执行面与行情服务的套接字 |
| 执行面 | 不变 | 加入 `trading-platform-dex-ipc` 补充组 | 不变 | 增加连 DEX 套接字 |

- 单元加固项与行情服务相同（`ProtectSystem=strict`、`InaccessiblePaths=@CONF_DIR@ @DATA_DIR@ @IMPORT_DIR@ @UPDATE_DIR@ -/run/trading-platform -/run/trading-platform-market`、`NoNewPrivileges` 等），另加 `StateDirectory=trading-platform-dex` 与 `StateDirectoryMode=0700`。安装器在首次迁移前自己建好这个目录（属主 DEX 账户、0700），不依赖 systemd 首次启动时创建。
- 代理配置按行情服务的 `market.env` 方式写进 root 所有的 `dex.env`，只含代理项。`TimeoutStopSec` 取 15 秒（模拟盘停机只需关库）。
- 账户与通信组**不论 `varLighter` 开关都创建**：执行面单元的补充组里写了 `trading-platform-dex-ipc`，组不存在执行面就起不来。

### 11.2 进程间协议

新目录 `src/dex/`：`main.ts`（入口）、`host.ts`（原 `src/service/varlighter.ts`，打开库、采集循环与页面路由表）、`server.ts`（套接字服务）、`ipc.ts`（执行面用的客户端）、`protocol.ts`、`probe.ts`（安装器健康检查）、`move-db.ts`（库复制，11.5）。执行面这一侧在 `src/service/dex.ts`。协议和行情服务一样走本机 HTTP，前缀 `/dex/v1/`：

| 操作 | 方向 | 说明 |
| --- | --- | --- |
| `GET status` | 执行面、安装器 → DEX | `{ build, instance, protocol: 1, process: { rss, heapUsed, loopDelayMs }, crash, token }`：健康检查、「服务器状态」、上次崩溃记录（11.7）、已收到的 token 摘要（11.4） |
| `POST page` | 执行面 → DEX | 通用转发：`{ method, path, query, body }` → `{ status, body }`。`path` 只取 `/api/varlighter/` 之后的部分，DEX 服务内部按原来 `http.ts` 的路由表分发。以后 DEX 加接口、改字段都不用改执行面 |
| `POST var-token` | 执行面 → DEX | 推送 Var token 状态（11.4） |
| `GET accounts` | 执行面 → DEX | 只读返回当前生效的场所账户概览（`DexAccountsState`：`accounts` 与 `problem`，不含私钥与 `apiKeyIndex`），供资产账本去重同步（`v0.110.0`） |

- 执行面 `http.ts` 的 `/api/varlighter/*` 分支改成：CSRF（所有 POST 在进路由前统一检查）与只读令牌范围检查照旧，再调用转发，拿到 `{ status, body }` 后用原来的 `send()` 发出，只读令牌的应答照旧经过别名替换。只读令牌白名单（`read-token.ts`）留在执行面，加新的令牌可读接口时才改执行面。`/api/shell` 的模块开关照旧取「有没有 varlighter 视图」，转发对象在就算开启。
- 传输照 `src/market/ipc.ts`：请求体一次写完（`content-length`），DEX 服务读完整个请求体才处理、才应答，所以不会出现 L204 第二段那种对端先关闭的情况；应答字节数设上限（32 MB，样本分页最多 1000 条，远低于上限）。中止信号按 L206 用 `anySignal`。
- 读超时：普通读取 10 秒；回测 120 秒（超时得 504，11.7）。请求体上限沿用各接口现有的上限（参数 64 KB，其余默认）。
- **失败处理分两种**，按 L204：
  - 确定没发出（连接都没建立、套接字不存在、DEX 在处理前拒绝或自己出错）：返回 503 `{ code: 'dex_unavailable', message: 'DEX 价差服务未就绪' }`，页面按确定失败显示。
  - POST 已经发出、应答丢失或超时：**不重试**，执行面直接断开浏览器连接（与控制面 `forwardedWrite` 相同），页面的写入钩子按网络错误显示「结果未知」，用户刷新后看实际结果。不把这种情况转换成 503。
- 现有写接口重放都安全：参数保存带 `revision`（重复提交得 409 `stale_revision`）；模拟盘平仓与清空只动模拟数据。S2 的实盘写接口另按 L204 带请求号。
- **没有进程内退路**：执行面只在带 `--dex-socket` 启动时开启转发；不带（检出目录直接运行、未装 DEX 单元的旧部署）时 DEX 价差返回 404，与 `"varLighter": false` 相同。这样执行面入口在任何情况下都不会导入 `src/varlighter/**`，指纹归属干净（11.3）。本地预览与测试由脚本在同一进程里起 DEX 服务和执行面（11.10）。

### 11.3 组件指纹

- `deploy/component-digests.mjs` 增加 `dex` 入口 `src/dex/main.ts`，按可达性算：从 DEX 入口可达的文件进 DEX 指纹；从执行面入口可达的进执行面指纹；两边都可达的共用文件（Var 询价传输模块、`src/any-signal.mjs`、`decimal.ts` 等）两边都算，改了两边都重启。
- 「不知道归谁就算执行面」的默认规则保留，只对「从执行面入口不可达、且在 `src/varlighter/` 或 `src/dex/` 下」的文件改算 DEX。脚本里加断言：执行面的可达集合里**不得**出现 `src/varlighter/` 下的文件，出现就打包失败。以后执行面误导入 DEX 代码，打包就会失败，而不是悄悄漏出执行面指纹。
- Var 询价的传输脚本（`scripts/` 下，现在按可达性加进行情服务）同样按 DEX 入口是否可达传输模块加进 DEX 指纹。
- 加一条安装测试：只改 `src/varlighter/` 下的文件，执行面、控制面、行情服务的指纹都不变，只有 DEX 的变。

### 11.4 Var token

DEX 服务不能读执行面数据目录，Var token（行情监控「原油」页保存的会话文件）改为**执行面推送**（`src/service/dex.ts`、`src/dex/main.ts`）：

- 执行面每 15 秒（`DEX_TOKEN_TICK_MS`）按现有规则读一次会话文件：权限须为 600、大小有上限、内容要有效，规则与原来 `varquote.ts` 读文件时一样。读出 `{ token, problem }`，`problem` 是文件不对时给页面的提示文案。
- 推送内容为 `{ seq, token, problem }`。`seq` 单调递增，从毫秒时刻起算（执行面重启后仍比之前的大）。**每一轮都推**，不论内容变没变，推送同时是 DEX 那边租约的续期。租约内 DEX 丢弃 `seq` 不大于已收到的推送（乱序、重放的旧推送不会覆盖新的）；租约过期后任何序号都收，执行服务所在机器墙钟回拨后也不会被一直拒绝。应答里带它当前生效的 token 摘要；执行面拿这个摘要与自己推的比，不一致就记一次日志，下一轮照推。同一轮先读 `status`：读失败（例如回测占着 DEX）时照推，沿用上一次的兼容判断，只有确知协议版本不兼容时才不推。
- DEX 只把 token 存在内存里，不落盘。**租约 60 秒**（`DEX_TOKEN_LEASE_MS`）：超过 60 秒没收到推送，DEX 视为没有 token、不再询价，页面提示「超过 1 分钟没收到执行服务推送的 Var token，已暂停询价」。执行面停了或卡住时 token 不会一直留在 DEX 里。收到空 token 立即生效，之后不再询价。按 L207，用户在行情监控里清空或更换 token 后，最迟一轮（约 15 秒）DEX 就不再用旧的。
- token 被 Var 拒绝后的暂停、单个标的的退避照旧在 DEX 服务里（`varquote.ts` 的 `TokenSource` 改为读内存，`problem` 文案照旧显示在实盘准备页）。执行面这段代码只读文件、推送、核对摘要，不含询价逻辑，以后改询价不动执行面。
- 选推送而不是让 DEX 服务直接读文件：文件在执行面数据目录，开放给 DEX 账户就得放宽数据目录或文件的权限；推送只让 token 这一项越过进程边界，方向是执行面 → DEX。凭据边界的变化：token 现在会出现在 DEX 服务内存里，DEX 服务的账户、目录与网络限制见 11.1。
- S2 实盘的 Lighter、Entropy 密钥由 DEX 服务自己的凭据文件持有（只有 DEX 账户可读），执行面不碰，届时另写方案。S2 假定不做 Var 腿的实盘下单；若要做，token 的用途变了，另行评审。

### 11.5 库的复制方式（root 不碰两个服务目录里的文件）

迁移和回滚都要在执行面数据目录（属主执行账户）与 DEX 状态目录（属主 DEX 账户）之间复制 `varlighter.sqlite`。两个目录都可被各自的服务账户写入，服务账户能事先放符号链接或硬链接，所以按 L201 与 [module-import.md](module-import.md)「身份与属主」的先例：**root 不按路径打开、复制、chown 这两个目录里的任何文件**，读写都交给目录属主身份的子进程（`runuser -u <账户> -- timeout 600 env -i node src/dex/move-db.ts …`，空环境），工具 `src/dex/move-db.ts`：

1. **复制前先停 DEX**（安装器 `systemctl stop`，确认已停才继续）。
2. **导出（源账户身份）**：主文件与 `-wal`、`-shm`、`-journal` 都用 `O_NOFOLLOW` 打开，按文件描述符核对是普通文件、单链接、属主为本账户，不符就拒绝。源目录所在文件系统的可用空间须不少于库（含旁路文件）大小的两倍。以真实 WAL 打开（按 L063，不用 immutable），先**不等待地拿独占锁**（`busy_timeout=0`、`locking_mode=EXCLUSIVE`、`BEGIN EXCLUSIVE; COMMIT`）：还有别的连接在用这个库就直接失败，WAL 回写也在锁内完成。`quick_check` 通过后用 `VACUUM INTO` 在源目录里做单文件副本（`journal_mode=DELETE`），再做一次 `quick_check`、统计各表行数与 sha256，标准输出先写一行头（字节数、摘要、行数），再写库的字节，最后删除临时副本。源端没有库时头里写 `missing`。
3. **root 只做管道**：把导出的标准输出接到导入的标准输入，`pipefail` 下任何一端失败都算失败，不落盘。
4. **导入（目标账户身份）**：目标文件系统可用空间须不少于库大小的两倍。在目标目录用随机名 `O_EXCL` 建临时文件，写入并核对字节数与摘要，`fsync`；以 `trusted_schema=OFF` 打开，只接受表与索引（含视图、触发器就拒绝），做 `quick_check` 并核对各表行数与头里一致。目标处已有库时先不等待地拿一次独占锁，还有连接在用就失败，然后把目标处原有的 `varlighter.sqlite` 与 `-wal`、`-shm`、`-journal` 一起改名为带时间戳的备份（`varlighter.sqlite.bak-<UTC 时间>`，只保留最近 3 份），最后把临时文件改名为 `varlighter.sqlite`，`fsync` 目录。任一核对失败就删掉临时文件，目标处原文件不变。源端没有库时，目标处原有的库也改名为备份（以源端为准）。
5. 源端的库原样留在原处，不删除、不改名；下一次反方向复制时它会被改名为备份。
6. 空间：库满量时约 1 GB（[varlighter.md](varlighter.md) 容量一节），每个方向复制时两端各要「库大小 × 2」的可用空间，目标处另有最多 3 份备份；执行面数据目录与 `/var/lib/trading-platform-dex` 通常在同一个系统盘上，首次迁移按约 3 GB 预留。1 GB 的库导出与导入各在几十秒内完成，600 秒超时留有余量。

### 11.6 首次升级、重入与回滚

**以哪份库为准**，由安装器在程序目录写的标记文件 `/opt/trading-platform/.dex-db`（root 所有，内容 `dex` 或 `executor`，没有这个文件按 `executor`）决定，不看文件新旧。标记**每次复制成功后立即写**（写临时文件、`sync`、改名、再 `sync` 程序目录），所以安装中断后重跑也知道该从哪边复制：

| 标记 | 这次的目标 | 动作 |
| --- | --- | --- |
| `executor` | 有 DEX 的版本，且 `varLighter` 开启 | 执行面健康之后：停 DEX、把库从执行面数据目录复制到 DEX 状态目录（11.5）、写 `dex`、启动 DEX |
| `dex` | 有 DEX 的版本，且 `varLighter` 开启 | 不复制；DEX 有变化或没在运行就重启 |
| `dex` | 没有 DEX 的版本（回滚到 v0.89.0），或写了 `"varLighter": false` | 在执行面重启之前：停用并删除 DEX 单元，把库复制回执行面数据目录、写 `executor` |
| `executor` | 没有 DEX 或 `"varLighter": false` | 只删除 DEX 单元（若有），不复制 |

`varLighter` 开关由安装器读 `config.json` 决定（以执行账户身份读）；在页面或手工改了这个开关后要**重新执行一次安装脚本**，DEX 单元才会装上或去掉。

**首次升级到 v0.90.0 的顺序**（会重启一次执行面，两个进程不能同时写这个库）：

1. 核验 DEX 账户与通信组（`ensure_dex_account`，与 `ensure_market_account` 相同的检查）：独立 UID 与主组；主组、通信组都不能是 0、执行账户、控制面、执行面通信组、行情账户与行情通信组的 GID；通信组里只有 DEX 账户与执行账户，也不能是别的账户的主组；DEX 账户不能加入其他组；控制面与行情账户不在 DEX 通信组里。行情账户的核验反过来也排除 DEX 的两个组。**不论 `varLighter` 开关**，只要目标版本带 DEX 组件就创建并核验，因为执行面单元的补充组里写了 `trading-platform-dex-ipc`。失败就保留当前服务，什么都不改；自动回退前对上一版也做同样核验。
2. 行情服务一步照旧（`activate` 里在执行面之前）。
3. 有序重启执行面，健康检查照旧。新执行面不打开 `varlighter.sqlite`，DEX 页面这时返回 503。
4. 按上表第一行复制库并写标记。
5. 启动 DEX 服务，`healthy_dex`（90 秒窗口，`probe_dex` 以执行账户加 DEX 通信组身份核对 `status` 的协议版本与组件指纹）。
6. 控制面一步照旧。

DEX 这一步在 `activate` 里的位置是：**执行面健康之后、控制面之前**。和行情服务相反，行情服务要在执行面之前确认，是因为执行面依赖它的行情；DEX 依赖执行面先放开这个库。

**失败时一律整体回退**，与行情服务相同：

| 失败点 | 结果 |
| --- | --- |
| 第 1 步核验失败 | 不升级，当前服务照常 |
| 第 3 步执行面健康检查失败 | 整体回退。库没复制，标记仍是 `executor`，DEX 单元按上表最后一行删除 |
| 第 4、5 步失败（首次迁移） | 整体回退到 v0.89.0。复制没成功时标记仍是 `executor`，旧执行面打开数据目录里原封未动的库；复制成功、DEX 健康失败时标记已是 `dex`，回退时按第三行把库复制回来（数据目录原有的那份改名为备份） |
| 以后的版本 DEX 健康失败 | 整体回退到上一版。只改 DEX 的版本执行面指纹不变，回退时执行面不重启（执行面的组件键没变）；DEX 回到上一版 |

第二轮审查后放弃了「只恢复上一版 DEX」：它需要单独的 DEX 回退记录与重入状态，收益只是在执行面也有改动的版本里保住执行面的新版；只改 DEX 的版本整体回退本来就不会重启执行面。

**回滚到 v0.89.0**（用 v0.90.0 及以后的安装器执行 `sudo bash install.sh --version v0.89.0`）：在执行面重启前停用并删除 DEX 单元，按上表第三行把库复制回执行面数据目录，再有序启动旧执行面。迁移后的采集与模拟盘记录都在。账户与通信组保留，不影响旧版本。库结构这一版不变，两个方向都不需要格式迁移。复制所用的 `move-db.ts` 取自目标版本（它不算进 DEX 指纹，固定下来的旧 DEX 组件目录里可能是旧的）；目标版本没有这个文件（回滚到 v0.89.0）时取 `/opt/trading-platform/dex` 指向的组件目录，清理旧版本时这个目录一直保留。

**已知限制**：用 v0.89.0 自带的安装器回滚（页面「系统更新」不会这样做，只可能手工执行旧脚本）时，旧安装器不认识 DEX 单元，DEX 服务继续运行，标记仍是 `dex`，旧执行面打开迁移前留下的那份库，迁移之后的样本不在其中。之后再用新安装器升级时按标记 `dex` 处理，DEX 状态目录的库照旧为准，旧执行面那几天写进数据目录的样本不并入（下一次回滚时被改名为备份，不删）。旧安装器清理旧版本时也不认识 DEX 组件目录，可能把它删掉；这时（且旧执行面开着数据目录里的库）新安装器回滚到 v0.89.0 会找不到复制工具或拿不到锁而失败（不丢数据，库仍在 DEX 状态目录、标记仍是 `dex`）。处理方式：先用新安装器升级到 v0.90.0 及以后（执行面换成新版、`dex` 链接重建），再回滚。README 的回退表写明「回到 v0.90.0 以前要用新安装器」。

**已知限制**：安装时 DEX 没变也会探测一次 `status`，正好碰上 DEX 在算一次长回测（最多 120 秒不应答）时探测超时，安装器按「运行的不是期望版本」重启 DEX，回测中断、页面得到 504，重试即可。

### 11.7 看得见的变化与可观测性

- DEX 价差页面、接口路径、只读令牌、MCP 工具、本机拉取工具都不变（它们都经 `/api/varlighter/*` 读取，不直接读库）。
- 以后只改 DEX 价差的版本：安装日志与「系统更新」写「DEX 价差服务已重启」，执行面、ASTER 划转与 ADL 不停；DEX 页面断开十几秒后恢复。
- 回测不再占执行进程。它仍在 DEX 服务主线程上同步计算，回测期间 DEX 的采集与 WebSocket 心跳会暂停；改用工作线程登记在 11.11。回测在 120 秒内没完成、或发出后应答丢失，页面得到 504「回测没有在限时内完成，请缩短区间后重试」（回测不改数据，不必按结果未知处理）。
- **「服务器状态」**：连接列表多一行 DEX 价差服务，由执行面的依赖巡检探测 `status`，不影响执行面就绪。DEX 进程的内存（rss、堆）、事件循环延迟来自 `status`，显示在这一行，按 L206 观察 DEX 进程的堆内存就看这里。
- **告警**：依赖巡检对 DEX 断开超过 **180 秒**（`DEX_DOWN_AFTER_MS`，比行情服务的 30 秒长，因为一次回测最多让 DEX 120 秒不应答）、实例变了（重启过）各发一条飞书。这是服务健康告警，经执行面现有的出站队列发；11.11 里「S1 不发告警」指的是 DEX 业务告警。DEX 崩溃时 crash-guard 把记录写在它自己的状态目录，`status` 带出上次崩溃的时间与摘要，执行面看到新记录就发一次「DEX 价差服务上次异常退出」，并按记录的键去重。
- **日志页**：页面「日志」与 MCP `logs` 只收执行进程的输出。DEX 服务的日志在 `journalctl -u trading-platform-dex`，S1 不并入日志页，登记为已知限制（11.11）。安装失败时打印的最近日志包含 DEX 单元。
- 首次升级到 v0.90.0 仍会有序重启一次执行面（11.6）。

## 12 实盘接入（S2，R3，方案已确认，第 1 步见 12.13；第 2 到 4 步由第 13 节取代）

2026-11-27 用户决定给 Lighter RH、Lighter 主网、Entropy 三个场所接实盘，并确认了 12.12 的五项。12.1 到 12.12 是动手前的方案，实际做法与方案不同的地方以 12.13 起各节为准。方案按 [code-review.md](code-review.md) 第 2 节写清行为、影响面、失败与回滚、不做的事。回滚版本 v0.100.1。外部接口的事实取自各场所公开文档与公开接口（2026-11-27 查），标「待实测」的要在真实账户上核对后才能依赖。

### 12.1 要改变的行为

- 实盘准备页的三项「待接入」（下单连接器、账户资金、监控告警）变成可以就绪的检查项。
- 配对可以单独切到实盘：信号、基线、入场出场规则与模拟盘完全相同，成交换成两条腿的真实 IOC 单。模拟盘照常并行，实盘另有一本账。
- **只有两腿都在这三个场所的配对能上实盘**：主网↔Entropy、RH↔主网、RH↔Entropy。带 Var 腿的配对仍只能模拟：Var 没有公开交易接口，成交接口未确认（11.4 已写明 S2 不做 Var 腿）。
- 实盘默认关闭。升级到带实盘的版本后不填凭据、不开开关，行为与 v0.100.1 相同。

### 12.2 三个场所的接口事实

| | Lighter 主网 | Lighter RH | Entropy |
| --- | --- | --- | --- |
| 是什么 | zkLighter | Robinhood Chain 上的独立部署，账户、密钥、nonce 都不与主网通用 | Hyperliquid 上的 HIP-3 盘，盘名 `io`（全名 EntropyIO，序号 10） |
| 接口 | `mainnet.zklighter.elliot.ai` | `api.rh.lighter.xyz` | `api.hyperliquid.xyz` 的 `/exchange` |
| 签名 | 自有方案（非 EIP-712），签名链号 304 | 同一签名器，链号 466324 | msgpack + keccak + EIP-712 `Agent`，secp256k1 |
| 凭据 | 账户编号、API 密钥编号（4–254）、API 私钥 | 同左，另一套；157 号也保留 | API 钱包（agent）私钥 + 主账户地址 |
| 保证金 | USDC | **USDG**（不是 USDC，页面文案要改） | USDC，按盘独立；不少标的只能逐仓 |
| 吃单 | 市价单 IOC，`price` 是最差可接受价，可 `reduceOnly` | 同左 | 没有市价单，用带限价的 IOC，可 `r` 减仓 |
| 订单自编号 | `clientOrderIndex`（uint48）+ 交易哈希 | 同左 | `cloid`（128 位） |
| 标准账户限制 | 手续费 0，吃单延迟 300 毫秒，全部请求每分钟 60 次 | 手续费 0 | 每 IP 每分钟 1200 权重 |

- API 密钥都不能提币：Lighter 的 API 密钥注册要 L1 钱包签名（用户自己在官方页面完成），Hyperliquid 的 API 钱包由主钱包 `approveAgent` 授权、最长 180 天到期。平台只持有这些交易密钥，不接触主钱包私钥。
- Lighter 的 nonce 按密钥严格加一；吃单在撮合时才检查保证金，被取消也消耗 nonce。重发前要先按交易哈希查结果。
- 待实测：Lighter 标准账户每分钟 60 次是否够两腿下单加核对；Entropy 各标的的逐仓限制与最小下单量；RH 上 USDG 的入金路径；Lighter WASM 签名器在服务器 Node 24 上的表现。

### 12.3 签名器

- **Lighter**：官方只有 Go 实现（`elliottech/lighter-go`，Apache-2.0），提供 WASM 构建供 Node 使用，同步接口，nonce 由调用方传入。仓库目前没有任何运行时依赖，这是第一份外来二进制，做法：CI 里从固定的源码提交构建 WASM，产物的 sha256 写进仓库，打包与启动时都核对；不从网络下载预编译文件。主网与 RH 用同一份签名器、不同链号。
- **Entropy**：自己写，复用 `src/aster/eip712.ts` 里已有的 secp256k1 与 keccak，加一个只覆盖下单动作所需类型的 msgpack 编码。用 Hyperliquid 官方 Python SDK 的签名向量做对拍测试。字段顺序与数字去尾零会改变签名，测试要钉住。
- 两个签名器都只在 DEX 服务进程里加载。执行面指纹不得包含它们（11.3 的打包断言已覆盖 `src/varlighter/`、`src/dex/`）。

### 12.4 凭据

- 存放（实际做法已改，见 12.13）：root 所有的 `/etc/trading-platform-dex/keys.json`（目录 0750、文件 0640，属组 DEX 账户），DEX 服务只读。不放在 DEX 状态目录里，服务自己改不了它（L201）。DEX 单元的 `InaccessiblePaths` 照旧挡住主配置目录。
- 录入：只走命令行 `sudo bash install.sh --set-dex-keys`，逐项询问、不回显，脚本化时从标准输入读；`--unset-dex-keys` 删除。**不做页面录入**：页面录入要让私钥经过浏览器、控制面、执行面三层，这三层现在都不碰 DEX 密钥。
- 吊销：删除文件即吊销。DEX 服务每次发单前核对文件仍在且未变（L207），不缓存到文件消失之后。
- 私钥不进日志、接口应答、报错、只读令牌的输出。`status` 只带「已配置哪些场所」与密钥指纹的前几位。
- 建议用户给每个场所开专用子账户，只放这个策略要用的保证金，API 密钥按场所支持的范围加限制（Lighter 的市场白名单与 IP 白名单）。

### 12.5 执行流程

一笔实盘开仓（平仓相同，两腿都带减仓标记）：

1. 信号来自行情流推送，与模拟盘同一个判断（`tradeDecision`）。发任何一条腿之前，在同一时间窗的两边盘口上一次算好两条腿的限价，校验都为正且当前盘口未越过（L100）；数量按两边步长分别取整后取较小值（L208）。
2. 把这笔的意图（两腿的场所、方向、数量、限价、自编号、nonce）先写库，再发单（L039、L095）。
3. 先发盘口较薄的一条腿（IOC）。成交量为零就结束，不算单腿。
4. 按第一条腿的**实际成交量**发第二条腿。第二条腿成交不足时，把第一条腿多出来的部分用减仓 IOC 平掉；减仓单有独立的重试上限，不要求报价新鲜（L084），用尽后转人工并告警。
5. 结果未知（超时、应答丢失）时不重发：按自编号与交易哈希最多查三次，过了交易所的请求有效期后读一次完整账户持仓作最终判定（L039、L091、L092）；持仓的更新时间要晚于成交时间才算数（L054）。
6. 同一配对连续两次单腿就暂停该配对的实盘，等人工恢复。

- 每个场所一个发单队列，保证 Lighter 的 nonce 连续；DEX 服务重启后先读 `nextNonce` 与账户持仓、订单，和库里的在途意图对账，对不上的配对停在「待人工核对」，不自动补单。
- 每轮（与采样同节拍）核对账户实际持仓与实盘账本：不一致就停开新仓并告警。持仓缺失这类可能瞬时的状态按间隔重试，不立刻判定（L110）。
- 页面的实盘写接口（开关、手动平仓、恢复暂停）都带请求号，转发断线后按请求号查结果，不重放（L204、11.2）。

### 12.6 风控

- 实盘有自己的一组限额，不沿用模拟盘的：单笔名义金额（默认 100 美元）、同时持仓笔数（默认 1）、名义合计、当日亏损上限（默认 20 美元）、单腿次数。到当日亏损上限后停开新仓，已有持仓照常按规则出场。
- 总开关在页面上，关掉后不再开新仓；另有「全部平仓并停止」，按 12.5 的减仓流程执行。
- 开实盘的前提是实盘准备页全部就绪。**「模拟盘至少 20 笔且净盈利」保留为自动实盘的前提**（现在是 0 笔）；金丝雀（12.8 第 2 步）不受这一条限制。
- 保证金不足、逐仓限制、最小下单量在发单前本地检查，不满足就不发，不靠交易所拒绝。

### 12.7 监控与告警

- DEX 服务不持有飞书配置。它把业务事件（开平仓、单腿、持仓不一致、限额触发、凭据文件消失、对账失败）放进一个有界队列，执行面在现有的 15 秒一轮里取走，经执行面的出站队列发飞书并按键去重。执行面停了时事件留在队列里，页面仍然显示。
- 实盘准备页的「账户资金」读各场所的保证金与可用余额，按单笔名义金额与限额算是否足够。
- 只读令牌与 MCP 能读实盘账本与事件，账户编号与地址照现有规则替换成别名。

### 12.8 分步

每一步单独发布、单独做 R3 审查，前一步在真实账户上核对过再做下一步。

| 步 | 内容 | 做完后能看到 |
| --- | --- | --- |
| 1 | 凭据文件与 `--set-dex-keys`（只录账户编号与地址）；三个场所的账户只读（保证金、持仓）。已做，见 12.13 | 「场所账户」「账户资金」两项按实际情况就绪；还不能下单 |
| 2 | 交易私钥的录入；两个签名器与对拍测试；库里加实盘表；下单、撤单、查单连接器；金丝雀：用户在页面上点一次，每个场所按最小下单量开一笔再平掉，核对成交、手续费、持仓回到零 | 三个场所各有一笔真实的最小成交记录 |

### 12.9 影响面、失败与回滚

- 改动只在 DEX 服务、安装脚本、页面与执行面的告警转发。执行面的执行器、划转、ADL、其他模块的账户都不涉及（11.1：这三个场所的账户只在 DEX 价差里出现）。
- 库：`varlighter.sqlite` 只加新表（实盘意图、成交、持仓、事件），不改已有表。回滚到 v0.100.1 时旧版本不认识新表，不受影响。
- 回滚：**回滚前要先在页面上「全部平仓并停止」**。旧版本不认识实盘持仓，回滚后这些持仓没人管；安装器在目标版本不含实盘、而库里还有未平实盘持仓时拒绝回滚并说明原因。凭据文件回滚后留在原处，旧版本不读；要去掉用 `--unset-dex-keys`。
- DEX 服务崩溃或被重启：停机前不发新单；`TimeoutStopSec` 从 15 秒加长到够一笔在途两腿收尾；重启后按 12.5 对账。
- 交易所不可用或限流：不开新仓；已有持仓到了出场条件而发不出单时告警，不无限重试。

### 12.10 本方案不做

- Var 腿的实盘。
- 挂单（只吃单）、自动划转与入金出金、自动调杠杆、跨场所保证金调配。
- Lighter 付费账户档位的申请与切换（标准账户吃单延迟 300 毫秒，见 12.11）。
- 页面录入私钥。

### 12.11 已知风险

- 模拟盘的信号多数来自一边报价滞后（一边先动、另一边还没跟上）。Lighter 标准账户吃单有 300 毫秒延迟；v0.109.0 起模拟盘按判断后 300 毫秒的一档成交（10.14），但不设限价、盘口冲击沿用判断时刻，实盘成交价仍可能差于模拟盘。金丝雀与手动单笔两步就是用来量这个差距的；差距吃掉价差时，自动实盘不该开。

- 两腿不是原子成交，单腿风险只能缩小、不能消除。

### 12.13 第 1 步实际做法（v0.101.0，R3，回滚版本 v0.100.1）

**范围比方案收紧**：这一版只录账户编号与地址、只做账户只读。交易私钥、两个签名器、实盘表挪到第 2 步，与下单连接器一起做：签名器没有连接器就无法在真实账户上核对，私钥提前放到服务器上也没有用处。这一版里服务器上没有任何能下单的东西。

**影响面**：DEX 服务（启动时取账户、每分钟读三个公开账户接口）、安装脚本（新目录、新参数、DEX 单元多两行）、实盘准备页（检查项）。执行面、控制面、行情面的代码与单元文件不变，`--set-dex-keys` 只重启 DEX 服务。库不变。

**凭据的存放与投递**（与 12.4 的方案不同）：

- 文件是 `/etc/trading-platform-dex/keys.env`，目录 root 0755、文件 root 0600，内容一行 `TP_DEX_KEYS=<base64url 的 JSON>`，JSON 为 `{ version: 1, lighter?: { accountIndex }, rh?: { accountIndex }, entropy?: { address } }`，未知字段与未知版本一律拒绝。
- DEX 账户打不开这个文件。systemd 以 root 身份按 `EnvironmentFile=-…/keys.env` 把内容放进服务的环境变量；服务启动的第一件事是取走并从 `process.env` 里删掉它（`src/dex/keys.ts` 的 `takeDexKeys`），之后启动的子进程不会继承到。
- **这不是对同一账户下其他进程的隔离**（审查 P1）：进程启动时的环境块在服务存活期间一直留在 `/proc/<主进程号>/environ`，以 DEX 账户运行的任何进程（包括 Var 传输的 python3 子进程，虽然它本来就以空环境启动）都能读到。执行面、控制面、行情面是别的账户，读不到文件，也读不到这个 environ。这一版的内容只有账户编号与地址，两者本来就能在各场所的公开接口上查到，所以按现状发布；**第 2 步放私钥之前必须换投递方式**（由 systemd 交给服务一个只读一次的描述符或凭据，并让 Var 传输子进程换账户或进一步隔离），不得沿用环境变量。
- 服务对这个文件只能 `stat`（`--keys-file`）。每次用账户前核对文件的 inode、大小、修改时间、状态变更时间（ctime）与启动时相同；文件被删或被换，内存里的账户立即停用，直到服务重启（L207）。启动时还要求文件大小与拿到的内容对得上：systemd 读完文件到服务第一次看文件之间被换成别的内容时，不把换过的文件当基准。这段空隙（服务启动的几百毫秒）里被换成**等长**内容的情形挡不住，服务会继续用启动时拿到的账户直到下次重启；用安装器录入不会走到这里（它写完文件才重启）。第 2 步换投递方式时一并解决。`guardedAccounts` 是唯一的取用入口，引擎拿不到未经核对的账户。
- 文件内容的 sha256 进 `dex-key`（`prepare_record`），所以录入、修改、移除都只重启 DEX 服务，执行面不动。真实 systemd 验收断言了这一点。
- 录入：`sudo bash install.sh --set-dex-keys`，依次问 Lighter 主网账户编号、Lighter RH 账户编号、Entropy 主账户地址，不回显；留空保留原值，填 `-` 去掉该场所；脚本化时加 `--dex-keys-stdin` 从标准输入读三行。`--unset-dex-keys` 删除文件。助手是 `src/dex/keys-setup.ts`，由 root 从目标版本运行，不进任何组件指纹；临时文件 0600、落盘后改名，读旧文件不跟随符号链接。安装器与助手的输出只说「已配置哪些场所」，不带编号与地址。
- 手动 `rm` 文件：服务在下一次读账户时发现并停用，准备页「场所账户」显示原因。
- **不要手工改这个文件，也不要往里加任何内容**：systemd 会把里面的每一行原样放进服务的环境（见上面的暴露面），服务只认助手写出的逐字节格式（少一个换行、多一对引号，大小就对不上，重启后仍显示「已更换」）。要改就用 `--set-dex-keys` 重写。
- 比较 ctime 的代价：任何只动元数据的操作（对 `/etc` 递归 `chown` / `chmod`、`restorecon`、备份工具建硬链接）都会让服务停用账户，直到 DEX 服务重启（`sudo systemctl restart trading-platform-dex`）。方向是失败即停用。安装器自己不碰没有改动的文件：重复执行 `--set-dex-keys` 且三项留空时，文件的内容与元数据都不变，服务不重启、账户照常可用（第二轮审查 P1，安装测试与真实 systemd 验收都有断言）。
- DEX 服务启动时在日志里写一行取用结果（「场所账户：已取到 N 个场所」或未使用的原因），不带编号与地址。

**账户只读**（`src/varlighter/accounts.ts`）：

- Lighter 主网与 RH：`GET /api/v1/account?by=index&value=<编号>`，公开接口，不需要签名。应答里的账户编号与请求的不一致时拒绝采用。
- Entropy：`POST /info`，`{ type: 'clearinghouseState', user, dex: 'io' }`，同样公开（统一账户模式的后续适配见第 15 节）。
- 引擎每 60 秒读一次，三个场所并行、各用各的 20 秒时限（一个场所不应答不影响另外两个），三分钟没读到算过期。读到的只有保证金、可用余额、持仓，放在内存里，不落库。
- 编号与地址不进准备页的视图、只读令牌的输出、日志与报错：视图里只有场所名、余额与持仓数。

**实盘准备页**：

- 新增「场所账户」：一个都没录是待接入；文件有问题、要用的场所没录、或录了但读不到（最近一次读取失败且没有三分钟内的读数，例如编号填错）是警告；其余是就绪。文件已写入而服务还没重启时提示等重启。
- 「账户资金」不再是固定的待接入：按每个已录入场所的可用余额对 100 美元（12.6 的单笔默认名义金额）判断，文案写明保证金币种（RH 是 USDG）。

**失败与回滚**：

- 文件格式不对、读不到账户接口：只影响准备页的这两项，采集与模拟盘不受影响。账户读取在引擎的后台任务里，失败不打断采样循环。
- 安装器写完文件后，后面的步骤失败（例如健康检查没过、DEX 服务没有重启成功）：运行中的服务发现文件已更换，停用账户并在准备页说明，直到下一次安装成功。方向是失败即停用。
- 助手在写临时文件与改名之间被杀，会在 `/etc/trading-platform-dex/` 留下一个 root 0600 的 `.keys.*.tmp`，没有进程读它，可以手动删除。
- 回滚到 v0.100.1：直接回退，不需要先做什么。旧版本的单元文件不引用 `keys.env`，文件留在原处没人读；不想留就先 `--unset-dex-keys`。

- 三个账户接口在服务器出口上的限流余量（每分钟各一次，远低于 12.2 的限额）。

**验证**：`test/dex-keys.test.ts`（编码与严格解析、取走环境变量、文件核对、录入助手与命令行、账户应答解析与身份核对、请求地址、准备页端到端）；`deploy/test-install.sh` 第 1 部分（参数校验、不回显、权限、只动 DEX 指纹、保留与移除）；`deploy/test-platform-systemd.sh` 迁移组（真实 systemd 下文件权限、服务账户读不到、环境变量送达、只重启 DEX、移除后不再送达）。审查记录在 [reviews/2026-11-27-dexspread-live-step1.md](reviews/2026-11-27-dexspread-live-step1.md)。

## 13 实盘：页面录入凭据，一步上线（R3，v0.102.0，回滚版本 v0.101.0）

2026-11-27 用户决定不按 12.8 分四步，改为：下单凭据直接在页面上录入，实盘一次做完。本节取代第 12 节里与之冲突的条目：12.4（凭据只走命令行）、12.8（分四步、金丝雀、先手动单笔）、12.10 的「页面录入私钥」不做、12.12 的第 3、4、5 项（「模拟盘至少 20 笔且净盈利」不再是实盘的前提）。12.2 的接口事实、12.5 的执行流程、12.6 的风控、12.7 的告警仍是依据，实际做法以本节为准。

### 13.1 改变的行为

- 实盘准备页最上面多出「实盘」一组面板：总开关与实盘配对、限额、下单凭据、实盘持仓、实盘成交与事件。
- 用户在页面上按场所录入凭据后，勾选配对、打开总开关。之后**模拟盘在勾选的配对上每开一笔仓，实盘就在两个交易所各下一笔真实订单；模拟盘平仓，实盘跟着平**。信号、阈值、冷却都用模拟盘的，实盘没有自己的一套策略参数。
- 只做两腿都能下单的配对（Lighter 主网、Lighter RH、Entropy 之间）。带 Var 腿的配对不上实盘，`orderPlan` 对 Var 腿给一条恒不通过的检查。
- 默认全关：没有录凭据、没有打开总开关时，本版本与 v0.101.0 的行为一样，不发任何订单。

### 13.2 凭据（`src/varlighter/livekeys.ts`）

- 存放：DEX 服务数据目录下的 `live-keys.json`（安装后是 `/var/lib/trading-platform-dex/live-keys.json`），由 DEX 服务账户所有，0600，写临时文件、落盘、改名。目录本来就只有 DEX 账户能进。
- 内容：`{ lighter?: { accountIndex, apiKeyIndex, privateKey }, rh?: {…}, entropy?: { address, privateKey } }`，未知字段拒绝。Lighter 的 API 密钥编号限 4 到 254（0 到 3 留给官方前端，RH 上 157 保留），账户编号须大于 0，私钥 80 位十六进制。Entropy 填主账户地址与 API 钱包私钥；**私钥对应的地址等于主账户地址时拒绝**（那是能提币的主钱包私钥）。
- 不走环境变量与 `keys.env`（L211：环境块在 `/proc/<pid>/environ` 里一直可读）。
- 只写不读：`POST live/keys` 的应答、`GET live`、核对清单、事件、日志、告警、错误信息都只说某个场所「已录入」。交易所返回的错误文本先经 `scrub`（去掉长十六进制与长数字串）才进备注与事件。Lighter 的查单令牌里带账户编号，只放在请求头里，不进任何日志。
- 路径：浏览器 → 执行服务（`src/http.ts` 读请求体，不记日志）→ 本机套接字 → DEX 服务。执行服务不保存、不解析凭据。**浏览器到服务器这一段靠 HTTPS 或可信网络**，页面上有提示。
- 页面录入的账户标识优先于安装时用 `--set-dex-keys` 录入的（没在页面录的场所仍用后者读余额）；`live-keys.json` 读不懂时账户只读与实盘一起停用，准备页显示原因。
- 移除：页面上按场所移除；该场所还有实盘持仓时拒绝（409）。同样，该场所有实盘持仓时只能给**同一个账户**换密钥（Lighter 比账户编号、Entropy 比主账户地址），换成别的账户会让旧账户上的持仓没人管，拒绝（409）。只读令牌读不到实盘接口（令牌的路径白名单里没有 `live`）；令牌能读的核对清单里有一项「实盘开关」，会带出开关状态、配对数、限额与停止原因（停止原因可能含持仓数量），不含凭据与账户标识。
- 与 12.13 的差别：这份文件 DEX 账户自己能读能写，所以以 DEX 账户运行的进程都能读到它。DEX 服务不启动第三方子进程以外的东西（Var 传输的 python3 子进程以同一账户运行，属于这个暴露面）。能接受的理由：填的是只能交易、不能提币的 API 密钥，且这些账户只放实盘限额内的保证金。

### 13.3 签名与下单（`hyperliquid.ts`、`lighter-signer.ts`、`orders.ts`）

- Entropy（Hyperliquid HIP-3）：msgpack 动作加 nonce 做 keccak，按 EIP-712 Agent 签名，`POST /exchange`。资产编号按 `perpDexs` 里盘的序号与合约在 universe 里的序号算。客户订单号（cloid）由本地编号生成，查单用 `orderStatus`。`test/dex-hyperliquid.test.ts` 对拍官方 SDK 的签名向量。
- Lighter 主网与 RH：官方 `lighter-go` v1.0.13（提交 `e8687faa091ae78de3da78fc338a11c48b4de87e`）在 CI 里用 Go 1.26.8 编成 WASM（`scripts/build-lighter-signer.sh`），`src/varlighter/signer/SHA256SUMS` 登记 `lighter-signer.wasm` 与 `wasm_exec.js` 的摘要，加载前核对，对不上不加载。仓库不存二进制，发布包里带构建产物（`deploy/package.sh` 缺文件即失败）。chainId 主网 304、RH 466324。每个签名器一个独立的 WASM 实例。Go 一侧对越界参数是静默截断的，所以 TypeScript 一侧先校验范围，签完再把 `tx_info` 里的字段与入参逐项比对，不一致不发送。
- 下单都是吃单 IOC：Entropy 用 `Ioc` 限价单，Lighter 用市价单类型加最差可接受价。Lighter 的 `sendTx` 被接受不等于成交，随后带查单令牌轮询 `accountOrders` 取成交量。
- 查单有三种结果（`ResolveOutcome`）：`done`（交易所给出了最终成交量）、`absent`（这次读成功了，但交易所没有这笔单的最终结果）、`unknown`（读失败）。**连接器不凭「过了多久」判零成交**，「查不到」怎么处理由 `live.ts` 结合账户持仓决定（13.4 第 6 条）。`ORDER_EXPIRY_MS` 是一笔单最晚还可能成交的时限：Entropy 60 秒（IOC 立即撮合，留出索引延迟），Lighter 两个场所 11 分钟（交易约 10 分钟过期）。
- Entropy 下单的应答里只有 HTTP 400、422、429 当作「没有受理」；其余读不懂的应答（含别的 4xx、5xx、超时）一律按结果不明处理。
- 一个场所的请求串行；Lighter 的 nonce 每次失败后重取。

### 13.4 两腿流程（`live.ts`）

1. 模拟盘开仓 → 检查（13.5）→ 用 `orderPlan` 定数量与两腿限价，实盘名义 = min(模拟盘名义, 单笔上限)。模拟盘的样本可能有一腿是旧的，所以跟单前、以及真正发第一腿前，再用两腿此刻的一档核对：买看卖一、卖看买一，任一腿没有报价或越过预演的限价就不跟这一笔（L100）。
2. **意图先落库再发单**（`live_positions` 表，带 `pending`）。进度（`step`）在发第一腿之前就推进，与 `pending`、本地订单编号（`liveRuntime.lastClientId`）一起落库；任何一次落库失败都不发单。这样进程在第一腿在途时重启，读回来的是「有一笔结果不明的订单」，只查单、不会再发一次第一腿。A 腿 IOC；零成交就放弃这次机会，不发 B 腿。意图落库后迟迟没发出第一腿的（超过 15 秒、总开关已关、已停止或模拟持仓已不在）直接作废。
3. B 腿按 A 腿的**实际成交量** × 乘数对冲，限价按当时的报价加限价保护算。这是有意的取舍：A 腿成交后首要的是把敞口对冲掉，不再用开仓时的 B 腿价卡它；价差因此变差的部分体现在这笔的盈亏里。
4. B 腿没成交或少成交：A 腿多出的部分立即用只减仓的 IOC 反向平掉（最多 3 次，逐次放宽限价），记一次单腿。回补不掉 → 这笔持仓标记「需要人工处理」，实盘停止并告警。只有 B 已补齐目标数量（A 实际成交量 × 乘数按 B 步长取整）时，A 剩下的那点才算乘数除不尽的取整余量，不算单腿、不回补；B 少成交哪怕一个步长都是真实敞口，哪怕低于最小下单量也照常回补，交易所不收时重试到上限转人工并告警。第二腿的意图一直落不了库（磁盘满、库坏）时不会无限重试：一分钟告警，十分钟转人工并停止。
5. 模拟盘平仓（或模拟持仓不在了）→ 两腿只减仓 IOC 平仓，最多 10 次、间隔 5 秒、逐次放宽限价；平不掉 → 需要人工处理。
6. **结果不明的订单绝不重发**（超时、断网、读不懂的应答）。判定顺序：按客户订单号查单，查到最终结果就采信（回报的成交量超过委托量的不采信，当作不明）；否则发出满一段时间（Entropy 20 秒、Lighter 60 秒）后现读账户，持仓相对发单前的变化量大于容差且不超过委托量 → 按变化量记成交；变化量为零 → **只有过了 `ORDER_EXPIRY_MS` 才算没成交**（Entropy 还要求这次查单读成功且查不到），在那之前继续等；其他对不上的情况继续算不明。15 分钟仍不明 → 需要人工处理。
7. 进程重启：读回未结束的持仓，带 `pending` 的先走第 6 条，不重发。服务停止时掐断在途请求并按「不明」落库。持仓记录里存着开仓时两腿的合约规格，配对后来被移出目录也照样能平仓。
8. 回补或平仓时取不到报价：不下单，等报价恢复；等满 60 秒告警，满 10 分钟标记「需要人工处理」。
9. 所有推进串行（一次只有一笔订单在途）。净盈亏只算已平掉的部分，含两腿手续费；成交价拿不到时按限价估，记「含估算价」。

### 13.5 风控与对账

- 开仓前：总开关开、配对已勾选、未停止、配对未暂停、两腿凭据都在、Lighter 腿的签名器可用、两边账户读数不超过 3 分钟且可用余额不小于本笔名义、未到同时持仓上限、当日（UTC）已实现亏损未到上限、下单预演全部通过（最小数量、最小金额、报价新鲜度、规格已核对）。任一条不满足就不跟这一笔，页面显示最近一次没跟的原因。
- 限额默认：单笔 100 美元、同时 1 笔、当日亏损 20 美元、限价保护 30 基点；页面可改，范围见 `LIVE_LIMIT_RANGES`。
- 同一配对连续两次单腿 → 暂停该配对。
- 对账：每 60 秒把记录的持仓与两边账户的实际持仓比对，连续两次对不上 → 停止（不再开仓，已有持仓仍按平仓信号处理）。总开关开着而没有实盘持仓时，也核对勾选配对两腿的合约应为零仓。对账只用 3 分钟内的账户读数；有持仓而账户连续 10 分钟读不到 → 告警。所以**这些账户必须专用**：手动开仓或别的程序交易都会触发停止（L205）。
- 停止与暂停落库（`liveRuntime`），重启不丢，重启后停止与「需要人工处理」的告警会重新给出（停止告警的键是「第几次停止」加原因，重启后不变，执行服务一侧不会重复发；恢复后再因同样的原因停止是新的一次，会再通知）；用户在交易所核对后在页面上「核对后恢复」。有需要人工处理的持仓时不能恢复，先在交易所处理干净，再用「已人工处理」（须输入 DISMISS，不发任何单）结束那条记录。
- 告警：停止、配对暂停、单腿、需要人工处理、当日亏损到上限。DEX 服务把告警放进 `status` 应答，执行服务每轮读到后用 `notifyOnce('dex-live:<键>')` 发飞书。DEX 服务自己不联网发通知。

### 13.6 接口与页面

- `GET /api/varlighter/live`；`POST live/keys`、`live/keys/remove`、`live/settings`、`live/close`、`live/dismiss`、`live/resume`。都只接受页面会话（写操作照现有规则要会话与同源校验），只读令牌不可用；模拟盘视图（只读令牌能读）的事件里不含实盘事件。`live/settings` 的 `on`、`pairs`、`limits` 都可省略，省略的保持原值：页面保存配对与限额时不带总开关，打开、关闭实盘时才带，免得用几秒前的视图把别处刚改的开关改回去。
- 页面 `web/src/varlighter/VarLighterLive.tsx`，放在实盘准备页最上面。私钥输入框是密码框，提交后无论成败立即清空；已录入的场所只显示「已录入」。打开总开关前弹确认，列出配对与限额。

### 13.7 影响面、失败与回滚

- 改动范围：DEX 服务（新增实盘）、执行服务（只多了转发告警，`src/service/dex.ts`）、页面、发布与 CI（构建签名器）。执行器、划转、ADL、其他模块的账户不涉及。
- 库：`varlighter.sqlite` 新增 `live_positions` 表与两个状态键（`liveSettings`、`liveRuntime`），不改已有表。
- **回滚到 v0.101.0 之前，先在页面关闭实盘并把实盘持仓平掉**。旧版本不认识 `live_positions`、`live-keys.json`，回滚后已有的实盘持仓没人管。凭据文件留在原处，旧版本不读；要去掉就在回滚前从页面移除，或删除该文件。
- **停用 DEX 价差模块（或升级到不带 DEX 组件的版本）同样要先关实盘、平仓**：安装器会停掉 DEX 服务，实盘持仓同样没人管。安装器对这两种情况都还没有拦截（12.9），靠人执行。
- 服务停止：正在推进的持仓在下一笔单落意图之前停下，不发单，也不留一笔从没发出的「在途」单；落意图失败时同样退回发送前，下一轮重来。只有「单还没交给连接器」的失败（专用的错误类型）才退回进度；单已成交、记成交的那次落库失败不往外抛，内存记着成交、库里留着在途意图，下一次保存补上，重启则重新查单，都不会再发一遍。
- 第二腿的意图一直落不了库而转人工时，库多半也写不进「需要人工处理」：**修好磁盘后先在实盘页核对并处理这笔，再重启服务**，否则重启后读回的是「第一腿已成交、待下第二腿」，会按当时报价补发第二腿；停止状态同样可能没落库。告警与持仓备注里都写了这句。这段计时只在内存里，服务在十分钟内反复重启时到不了转人工，只有一分钟时的告警。
- 交易所不可用或限流：开仓条件里账户读数会过期 → 不开新仓；已有持仓平不掉时重试到上限后告警，不无限重试。
- DEX 服务崩溃：意图已落库，重启后按 13.4 第 7 条处理。崩溃到重启之间没有人盯仓，这段时间的风险靠单笔限额兜住。
- 12.9 里两项没有做：安装器在回退到不认识实盘的版本前检查「实盘已关且无持仓」的拦截没有做，回滚前的检查靠上一条由人执行；`TimeoutStopSec` 仍是 15 秒，没有加长，因为停止时在途请求被掐断并按「不明」落库，重启后只查不发，不需要等订单走完。

### 13.8 已知风险与没有做的

- **没有在任何真实账户上下过单**。签名、下单、查单的格式来自各场所的公开文档、官方 SDK 与签名向量对拍，全部「待实测」，清单见 [live-results.md](live-results.md)。第一次打开实盘请用最小限额并盯着页面与交易所。
- 模拟盘的信号多数来自一边报价滞后；Lighter 标准账户吃单有 300 毫秒延迟，v0.109.0 起模拟盘已按延迟后的一档成交（10.14），实盘成交价仍可能差于模拟盘（限价、排队与部分成交）。没有「模拟盘先盈利」这道前提之后，这个差距直接体现为实盘盈亏。
- 两腿不是原子成交，单腿风险只能缩小、不能消除。
- 实盘没有独立的止损：平仓完全跟随模拟盘（含模拟盘的止损与最长持有）。模拟盘被清空或配对被停用时，对应的实盘持仓按「模拟持仓不在了」平掉。
- 没有做：Var 腿、挂单、自动划转、调杠杆、金丝雀按钮、手动开单、只读令牌与 MCP 读实盘。
- 页面上已录了凭据的场所，`keys.env` 里同一场所的条目有问题时不再提示（页面录入的优先）。
- Lighter 的查单接口（按客户订单号读 `accountOrders`）与账户持仓里的合约名是否与目录一致，都只按文档与替身应答写的，待实测；它们不对时的表现是订单长时间「结果不明」直至转人工处理，不会重发。查单接口不可用时，每笔 Lighter 单都要等 60 秒按持仓判定，第二腿没成交要 11 分钟才回补，单腿敞口会明显变长。
- Lighter 判零依赖交易的有效期：签名后核对签出的 `ExpiredAt` 在 10 分钟以内，判零用发出后 11 分钟。服务器时钟比 Lighter 慢一分钟以上时这一分钟余量不够，服务器须开着时间同步。
- Entropy 查单查到「还挂着」时保持不明、不判零（IOC 理论上不会挂单）。
- 发单前的报价核对只防「样本之后价格变了」，不防「某个市场的推送悄悄停了」：它用的一档与样本同一来源，新鲜度上限同样是 75 秒。
- 登记未改：回补、平仓的次数在落意图之前就计入，落意图失败（磁盘短时写不进、停止中）也会消耗次数，可能提前转人工且备注写成「平不掉」；平仓结束时落库失败，持仓在本进程内仍占着配对与同时持仓的名额，重启后按库重新处理；以上都不发单、不错记。交易所报错里 1 到 4 位的数字（例如短的账户编号）不会被 `scrub` 去掉；签名器实例运行中崩溃后不会自动重建，要重启服务或重新录入凭据；对账读数记的是读完的时刻；转人工时落库失败的话停止状态只在内存里。
- WASM 构建的可复现性只由 CI 上的摘要核对保证；换 Go 版本或 `lighter-go` 版本要同时更新 `SHA256SUMS`。

## 15 Entropy 统一账户余额读取（R3，v0.108.1，回滚版本 v0.108.0）

2026-11-27 实测 Hyperliquid 公开接口确认：当 Entropy 账户启用统一账户模式（`unifiedAccount`）时，闲置 USDC 集中存放在统一账本（`spotClearinghouseState` 的 `token === 0`），按 HIP-3 盘查 `clearinghouseState(dex: 'io')` 在无持仓时 `accountValue` 与 `withdrawable` 均返回 `0.0`，有持仓时 `withdrawable` 也常为 `0.0`。因此准备页「两边账户资金」、实盘开仓前余额校验与「账户资产」页签都会把统一账户误判为可用 `0.00 USDC`。

- **要改变的用户可见行为**：`src/varlighter/accounts.ts` 的 `fetchAccount` 读取 Entropy 账户时，使用同一超时信号并行读取 `clearinghouseState(dex: 'io')` 与 `userAbstraction`：
  - `default` / `disabled`（标准分账模式）：沿用原口径，直接返回 `io` 盘 `clearinghouseState` 的权益、可用余额与持仓。
  - `unifiedAccount`（统一账户模式）：再以同一信号读取 `spotClearinghouseState`，从中提取 `USDC`（`token === 0`）的 `total` 作为 `collateral` 与 `equity`、`Math.max(0, total - hold)` 作为 `available`（并提取非零现货余额进 `assets` 供账户资产页展示）；`positions`、`marginUsed`、`unrealizedPnl` 仍取自 `io` 盘 `clearinghouseState`。
  - `portfolioMargin`（组合保证金）、`dexAbstraction`（旧版 DEX 抽象）与未识别模式：直接读取失败并给出明确原因，不静默返回 `0.00`；实盘准备页与账户资产页照既有时限降级提示，开仓前检查照常拦截。
- **影响面**：改动仅涉及 `src/varlighter/accounts.ts`、对应单元测试（`test/dex-keys.test.ts`、`test/dex-accounts.test.ts`）、本地预览脚本 `scripts/dev-varlighter.ts` 及文档；不改动 `live.ts`、`engine.ts`、实盘下单签名与平仓路径、凭据文件格式、`varlighter.sqlite` 库结构、前端组件与部署安装脚本。
- **失败与回滚**：
  - `userAbstraction`、`clearinghouseState` 或统一账户下的 `spotClearinghouseState` 任一失败或字段无效（包括 `token === 0` 重复、币种非 `USDC`、非 `token === 0` 却名为 `USDC`、负值）时整个读取失败，不回退使用 `0.00` 或旧值覆盖时限之外的状态；先判 `userAbstraction` 模式再解析 `clearinghouseState`，避免不支持模式被结构异常错误掩盖。
  - 回滚版本为 `v0.108.0`：库结构与配置无变更，直接回退即可。
- **本次不做**：
  - 不对 `portfolioMargin` 做多币种抵押率/可借余额换算；暂不读取或折算 `USDT0` 作为 `io` 盘保证金（`meta(dex: 'io')` 核实 `collateralToken` 为 `0` 即 `USDC`）。
  - 不改变实盘下单/平仓/对账状态机。
- **验证与待实测**：`test/dex-keys.test.ts`（`parseEntropyUnifiedBalance` 正常/空条目/超 200 项截断/异常与重复 `USDC` 拒绝、`default`/`disabled`/`unifiedAccount` 读取与信号透传中止、`portfolioMargin`/`dexAbstraction`/未知模式/现货账本失败拒绝、准备页端到端）；`test/dex-accounts.test.ts`（统一账户资产视图、快照写入与 D4 不泄露地址）；审查记录见 [reviews/2026-11-27-entropy-unified-account.md](reviews/2026-11-27-entropy-unified-account.md)。`unifiedAccount` 存在 `io` 盘活跃持仓与明显浮盈亏时的 `spot.total`/`hold`/`tokenToAvailableAfterMaintenance` 对账表现已记入 [live-results.md](live-results.md) 待实测。
