## 第一轮（两路独立审查）

审查 A 核实：三种写操作都先落盘为“待核对”再发送，只有 `rejected` / `not-sent` 算明确拒绝；执行与取消在准入锁内，核对循环不在锁内，`rfqVersion` 与 `state.rfq !== rfq` 两道检查丢弃过时读取；执行前复核报价覆盖、数量、价格、剩余时间、合约、日历与按报价价格的风险上限；成交转任务、委托记录与跟踪在同一次同步保存中写入，可幂等重放；回退到 v0.16 兼容。审查 B 核实：CSS 与工作台 2f0593d 对应行一致、无内联样式、390 宽不横向溢出、正负号与手续费口径和服务一致、未登录处理、防重复提交、路由与测试。

## 第二轮（复审修复差异）

无 P0、P1。复审核实：兜底任务（订单号为空）不发成交请求、不计失败，收益页显示“开仓成交历史尚未补齐”，退役按 `acceptedAt = createdAt` 匹配；已有跟踪时询价结束、拦截解除、飞书只发一次；回到等待报价的持久化无遗漏；应答身份不符时保持待核对直到交易所终态或人工恢复；文档 `sqlite3` 命令与 `store.ts` 表结构一致，`restore` 接受 `rfq: null`。

| 级别 | 问题 | 处理 |
| --- | --- | --- |
| P2 | 成交列表持续读失败（接口参数或权限实盘不对）时异常进外层，走不到兜底，仍永久锁死且不发飞书 | 已修：成交列表单独捕获，读失败按“没有成交记录”计时与兜底，原因写进页面提示与兜底说明；已补用例 |
| P2 | 兜底等待从执行发送时刻算，重启或长时间等待成交后首次看到已成交就立即兜底，没有等待期 | 已修：从本进程首次看到已成交起算（内存，重启后重新计时）；已补用例（发送 5 分钟后首次看到成交仍等待 2 分钟） |
| P3 | 已有跟踪而未接管的询价持仓没有保护：原策略平掉后定时开仓不再被拦 | 已修：提示与文档写明核对前先关闭定时开仓 |
| P3 | 未接管时丢掉了成交列表不一致的原因 | 已修：拼进错误说明与飞书 |
| P3 | 发送前第二次复核或停止检查失败时没恢复保证金基线，与回到等待报价不对称 | 已修：这两处失败也恢复执行前的基线 |
| P2 | （作者浏览器复查发现）第一轮“状态变化清掉旧提示”的修法把创建与执行的应答提示也立即清掉：应答后刷新，状态一变提示就没了 | 已修：提示记下它描述的询价状态（应答的状态，或设置时页面显示的状态），只在页面状态与之不同时清掉；浏览器复查创建与执行提示都能看到 |
| P3 | 新增 RFQ 拒绝码未逐个对照 Bybit 错误表核实 | 登记：码值取自工作台 `bybit.py`，实盘前对一次 110300 / 110301 / 110304 的含义 |
