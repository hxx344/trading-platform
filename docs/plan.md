## 2 业务规则

规则以执行器现有实现为准（`docs/executor.md`《关键语义》），其中 ADL 的四项是 2026-11-11 用户已定的决定，与工作台 Python 版不同：

- 完成后自动结束：两账户事件标的多空总量相等即完成；有结果未知的原单时观察 10 分钟后自动关闭（Python 是保持 hold、无期限观察）。
- 时限 1800 s 只累计减仓中（active）的时间；停止后可在页面“重新开始自动减仓”（Python 计入受阻时间、停止后无出口）。
- 减仓单为只减仓市价单，单批名义上限默认 1000 USDT。
- 残差小于最小下单量记为完成（Python 一直受阻）。
- 对冲容差（2026-11-12 用户决定）：每个标的两账户合计的多空总量之差不超过较大一侧的 0.5% 即视为对冲。ADL 事件里偏差在容差内的标的不减仓、记为残差完成；超出容差的开始减仓后一直减到两侧相等（本事件或其父事件发过减仓批次的标的不再按容差提前停；双向持仓同一账户同时有多空时按各方向数量合计，容差基数随之变大）。接管检查与持仓面板的“一致”同样按此容差判断。

划转规则与 Python 一致：同一主账户下两个子账户，只划 USD1。
- 触发与金额：两侧可用余额之差严格大于门槛（默认 10）才划转，从多的一侧划到少的一侧。金额取以下几项中的最小值：差额一半、单次上限（1000）、转出侧可提额、转出侧可用减保留额。
- 保留额与冷却：保留额 = 权益 × 保留比例（0.05），冷却 30 s，最小 1。
- 结果未知不重发：nonce 过期（最后更新 + 120 s）后读一次流水，打标签结清。

第一阶段要补齐的差异：

- 绝对现金保留额（Python 的 `long_reserve`/`short_reserve`，默认 0 即关闭）：转出侧保留额取 max(权益 × 比例, 该侧固定保留额)，配置项 `longReserve`/`shortReserve`（已完成）。
- 余额与流水用各子账户自己的凭据读取；主账户只读子账户列表、发划转（与 Python 一致；“主账户直接读子账户余额”未经实测，不依赖）。
- 双向持仓模式下减仓单不带 `reduceOnly`、按 `positionSide` 减仓；单向（BOTH）才带 `reduceOnly`（与 Python 一致）。

## 3 架构

```
trading-platform/
  src/            执行器核心（来自 platform/executor）：存储、租约、两腿任务、划转、ADL、
                  持仓展示、HTTP；原型入口 main.ts 与模拟场所
  src/aster/      真实 ASTER：签名（EIP-712，已在真实划转探测中用过）、请求预算、
                  划转 / ADL / 持仓连接器、用户推送（ADL 即时发现）
  src/live/       Binance / Bybit 真实下单连接器、启动检查、金丝雀
  src/oil/        原油行情读取（两腿任务本身在执行器核心里）
  src/options/    期权 Greeks：客户端、期权链、策略、下单、引擎、收益、询价、状态库
  src/monitor/    行情监控：采集与存储
  src/asset/      资产账本：导入、读取、写入与锁、计算口径
  src/vendor/     复制自工作台的行情与传输文件（改动处在文件头注明）
  src/service/    服务入口：配置与密钥文件、启用检查、各模块接线、从工作台导入、
                  飞书发件箱与定时摘要、页面日志
  web/            页面（React + Vite），构建到 web/dist
  probes/         真实接口探测脚本（ASTER 划转）
  scripts/        本地预览与测量脚本
  deploy/         install.sh、systemd 单元、示例配置
  test/           离线测试
```

运行形态：一个 Node 24 进程（systemd 服务 `trading-platform`，系统账号同名），数据在 `/var/lib/trading-platform`，配置在 `/etc/trading-platform`，程序在 `/opt/trading-platform`。

- 配置 `config.json`：密钥文件的绝对路径 `secretsFile`、配对列表（`id`、主账户和多空子账户的凭据名、划转参数与 ADL 设置的初始值）、本机端口（默认 4720）、请求预算。1–20 个配对，同一子账户只能在一个配对里。
- 密钥 `secrets.json`：每个 ASTER 账户的 `user`、`signer`、`privateKey`，以及飞书机器人 `webhook` 与签名密钥；两个凭据名不能指向同一个钱包。文件属服务账号，权限 600，最大 64 KiB；启动时校验私钥能推出 signer。
- 请求预算：ASTER 按出口 IP 计请求权重，工作台 ASTER 模块共用同一 IP 并自限每分钟 1800。本项目默认每分钟最多 600，可配置；ADL 读取与减仓优先于划转。
- 飞书：发件箱落在独立的 `notify.sqlite`，首次启动从当前事件开始（不补发历史）；单次超时 10 s、失败指数退避（最长 5 分钟）、保留 7 天，同一持续问题 30 分钟内只发一次；发送失败不影响划转与 ADL。告警项：划转结果未知与结清依据、已启用配对保证金异常（与工作台一致：划转受阻、两侧可用余额差超过划转门槛（严格大于）或检查失败；差额在门槛内、低于最小划转额等「无需划转」不算）持续 60 秒告警、未恢复每 2 分钟重复、恢复通知一次，有划转确认成功即重新计时，消息带两侧可用余额、差额与门槛、ADL 发现、受阻、停止与完成、服务启动与停止（含租约丢失、处理循环连续失败）。未配置机器人时只写日志。
- 用户推送：每个子账户一条 ASTER 用户推送（listenKey，30 分钟续期、23 小时 50 分计划重连、0.5–30 s 退避），只用来更快发现 ADL；断开时按 60 s 一次的强平历史扫描兜底。ASTER 会断开客户端长时间不发数据的连接（只回应服务端 ping 不够），所以每 30 s 发一次 `LIST_SUBSCRIPTIONS` 保活；收到过应答后 95 s 没有任何消息就判定连接已死并重连。断开日志带关闭码、错误文本与连接时长（v0.10.0）。
- 飞书定时运行摘要（v0.10.0，`src/service/summary.ts`）：照工作台 `hourly_summary.py` 的卡片，默认每 60 分钟一张，发往 `feishuScheduled`（没有时发往告警机器人）；排程存在 `notify.sqlite`，重启沿用，停机错过的周期只在启动约 2 分钟后补发一张，间隔可在设置页修改（v0.10.1，页面值优先于 config.json），也可立即发送一张，换机器人后先发一张，发送失败隔 1 分钟重试、3 次后放弃本期。
- 页面日志（v0.10.0，`src/service/service-log.ts`）：服务写到 stdout / stderr 的每一行另存一份到 `logs.sqlite`（保留 14 天、最多 5 万行、每分钟最多 1200 行），「日志」页分页读取 `/api/logs`；journal 仍是完整记录。
- ADL 只处理已启用的配对（以及停用前仍有未结束事件的配对），历史扫描从配对启用时开始，不回看启用前。

## 4 切换与回退

切换一个配对：

1. 在页面「设置」→「从工作台导入配对」里读取工作台、勾选并导入（等价的命令行是 `sudo bash install.sh --import-workbench`）：从本机工作台导入配对设置（保证金平衡各项、ADL 自动减仓与单批上限）、三个账户凭据和飞书机器人，登记后默认停用，服务自动重启。只读工作台数据。也可以手写 `config.json` 后执行 `sudo bash install.sh`。配置里的 `transfer` 与 `adl` 只在配对首次登记时作为初始值，之后以页面「设置」为准。
2. 在工作台暂停并删除该配对，确认工作台“账户写入”里这三个账户没有未结清的划转。
3. 页面点“启用”。启用前检查以下各项，任一不满足就拒绝并说明原因：
   - 凭据：三个账户凭据有效，主账户能列出两个子账户，且子账户未冻结。
   - 外部划转：两个子账户最近 10 分钟的流水里没有不属于本项目的 `SUBUSER_ASSET_TRANSFER`。这是检测工作台配对是否仍在运行的旁证。
   - 外部减仓单：两个子账户没有客户订单号以 `adl_` 开头的挂单。这类挂单是工作台 ADL 遗留的。
   - 两侧对冲：两个子账户合计每个标的多空总量之差不超过较大一侧的 0.5%。ADL 只从启用时开始扫描，停用工作台到启用之间发生的 ADL 由这一项拦下，须人工处理到两侧一致再启用。

   配置里删掉的配对在服务启动时自动停用；改了账户的配对重新登记为停用。
4. 启用后先观察一轮划转。

回退：在本项目停用该配对。停用前须确认没有未结清的划转与未结束的 ADL 批次，页面会提示。之后在工作台重建配对。本项目的库不回写工作台。

## 6 尚待实测（接真实账户时确认）

- 子账户列表行是否带钱包地址（2.6b 实测能核实归属，但未记录字段）；不带时按各子账户自己的 `accountId` 对应。
- `positionRisk` 的零仓位行是否带 `updateTime`（缺失时按 0 处理，执行器视为未证明已反映）。

2026-11-13 第一次实盘（[live-results.md](live-results.md)）已核实：划转回执都不带交易编号，93 笔全部按回执结清，没有出现结果未知；连续约 16 小时没有限流（429/403）或权重超限；ADL 历史扫描按正常窗口连续运行无错误。新发现：用户推送约每 6 分钟断开一次（日志只有“连接出错”），不影响划转，ADL 退回定时读取；原因已查明并在 v0.10.0 修复（见 live-results.md《用户推送断开的原因》），修复后的效果待服务器上确认。以下仍未实测：

- nonce 有效窗口按 120 s 计（ASTER 文档 ±60 s，未实测；第一次实盘没有结果未知的划转）。
- ADL 减仓单回报的 `updateTime` 是否不晚于持仓 `updateTime`（若晚于，每批多等 120 s）。
- `forceOrders` 查询跨度上限（重新启用时扫描从启用时刻开始，正常运行窗口约 2 分钟，不依赖长跨度）。
- 网关拒绝（HTML 429/403）与 `X-MBX-USED-WEIGHT-1M` 响应头的真实表现（替身已覆盖）。
- 本服务为同一子账户申请 listenKey 是否会让工作台已有的推送失效（工作台停用该配对后已不依赖，但同账户其他用途需留意）。
- 高负载下流水入账延迟（2.6b 实测 50–206 ms，仅 2 个样本）。
- 用 `--pairs` 分批迁移时，工作台与本服务同时用同一个主账户 API 钱包签名（工作台尚未迁移的配对仍在划转）：ASTER 的 nonce 规则是否允许两个进程交错使用同一签名钱包未实测；第一批切换后观察两边划转是否出现 nonce 拒绝。

## 7 已知限制

- 请求额度：每个配对空闲时每分钟约 260 权重（两侧余额每 5 s、持仓显示每 15 s、ADL 历史每分钟）；未配置 `budget` 时按配对数自动取值，最多约 6 个默认配对，再多需调大 `checkIntervalMs`。
- 停用配对即停止该配对新的 ADL 检测；停用期间发生的 ADL 不处理，重新启用前接管检查要求两侧每个标的多空总量偏差不超过 0.5%。
- 从工作台导入后、在工作台删除配对之前，两边同时运行：本服务已为停用的配对建立子账户推送并读取余额与持仓（计入同一出口 IP 的请求权重），但不划转、不检测 ADL。两边都不注销 listenKey，推送互不影响；配对多时两边合计权重是否逼近 IP 上限待实测，建议导入后尽快逐个切换，或用 `--pairs` 只导入马上要切换的配对。
- `--import-workbench` 在导入后的配置检查或启动失败、或安装被信号中断时恢复导入前的 `config.json` 与密钥文件（含属主与权限）；服务启动与健康检查期间收到的停止信号推迟到检查结束（其中的 systemctl、等待与日志读取不受 Ctrl-C 影响，终端断开也不中断）；回退到 v0.1.0 前须先移除配置里的 `adl` 字段，旧版本不认识它。
- 页面导入经 root 导入助手完成：服务把请求写进 `/var/lib/trading-platform-import`（root 所有、服务组可写，770），`trading-platform-import.path` 启动一次性的 root 单元处理。
  - 助手只接受服务账户所有、单一硬链接、不超过 4 KiB 的普通请求文件，读后删除；结果写为服务账户所有的 600 文件并原子替换。
  - 助手持安装锁（最多等 100 秒），与 `install.sh` 不会同时改配置；等待超过 2 分钟的请求作废不执行。
  - 页面只导入工作台已开启保证金平衡的配对（服务账户由此拿不到别的配对的密钥；命令行导入不受此限）。
  - 写入前把两个文件的原文、本次写入内容的摘要、请求编号和开机编号记入配置目录的 `.import-undo.json`（root 600），导入后以服务账户运行 `--check-config`，通过才重启；重启后 90 秒内没有正常监听（与安装脚本同一判据）就逐字节恢复导入前的两个文件并再次重启。
  - 助手中途被终止（单元 12 分钟上限）时，`ExecStopPost` 或下次启动按撤销记录处理：两个文件仍是导入前或导入写入的内容才恢复；之后被改过（`install.sh`、手动）则保留现状；服务器重启过或记录已超过 15 分钟、两个文件都是导入写入的内容且检查通过则保留（服务可能已在上面运行），只写了一半则恢复；记录无效时移到 `.import-undo.json.invalid`，不动配置。
- 页面导入尚未处理：请求恰在助手最后一次取件后、退出前写入时，`PathChanged` 不再触发，页面约 2 分钟后提示没有响应，重新操作即可；导入改了配置，下次执行 `install.sh` 会因配置变化再重启一次服务；助手不接收 `--workbench-data`，工作台数据目录须写在其环境文件的 `DATA_DIR` 或用默认位置；助手单元未启用 `ProtectSystem=strict`（读库子进程可能需要在工作台数据目录建 `-wal`/`-shm`）。回退到 v0.3.0 之前的版本时导入单元保留，页面不再提供导入，可 `systemctl disable --now trading-platform-import.path`。
- 首次安装（没有 `config.json`、密钥文件和运行记录）写入空配置并启动服务；数据目录已有 `executor*.sqlite` 而配置丢失时不生成空配置，以免启动时停用全部已知配对。
- 页面会话保存在数据目录 `http-session`（600），cookie 有效 30 天，文件满 30 天后在下次启动时更换；数据库里只记会话的摘要。拿到这个 cookie 的人在有效期内都能操作页面，与读取 `access-url` 的权限相同；要让所有已登录的浏览器立即失效，删除该文件后重启服务（`install.sh --set-password` 换密码时会自动删除）。
- 页面走 HTTP：设置 `host` 为 Tailscale IP 时，链路加密靠 Tailscale（WireGuard），cookie 不带 `Secure`；不要把 `host` 设成公网地址。登录密码的错误次数只按进程计数（不分来源地址），同一 tailnet 里有人反复输错会让本人也暂时登录不了，此时用 access-url 链接登录（同时解除锁定）或等锁定到期；一小时无错误或服务重启会清零计数。
- cookie 不区分端口：设置 `host` 后，同一台机器同一地址上其它端口的 HTTP 服务（例如工作台），只要浏览器经该地址访问过，也会收到本服务的会话 cookie。走 HTTP 用不了 `__Host-` 前缀；这类服务须是自己信任的。
- 导入器读取工作台数据库：以 root 运行时，在子进程里以数据库属主的身份只读打开（不带附加组；数据库是符号链接或非普通文件时拒绝），正常加锁，读到工作台尚未写回主文件的记录；SQLite 读取时可能新建的 `-wal`/`-shm` 归工作台账户，不影响工作台写库。超出请求预算、超过 20 个配对或主账户与别的配对子账户共用 API 钱包的配对逐个跳过并说明原因，其余照常导入；现有密钥文件或配置本身未通过检查时整次不导入。建议通过 `install.sh --import-workbench` 运行；单独以 root 运行导入器时，写出的文件沿用被替换文件（或所在目录）的属主。

- EIP-712 签名（`src/aster/eip712.ts`）是本仓库的零依赖实现，已与 ethers 及 Python `eth_account` 逐字节对照，并在 2.6b 真实划转中用过；它不是常量时间实现（私钥只在本机签名，远端观察不到时序）。以后如引入运行时依赖，换成经过审计的库（如 `@noble/curves`）。
