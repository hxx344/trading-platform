# 在线更新

页面侧栏「系统」组的「系统更新」：查看当前版本与最新正式版，确认后由服务器上的 root 更新助手执行一次 `install.sh --version <最新版>`。对照工作台的同名功能（project-aggregation `src/UpdateStatus.tsx` 提交 `c03c83f`、`src/updates.css` 提交 `9222ed6`、`docs/deployment.md`），按本服务已有的「从工作台导入」root 助手方式做成更轻的一套。

## 公开行情独立更新（R3）

安装器增加 `trading-platform-market.service`。从 v0.66.0 等双进程版本首次升级时，安装器先启动并核验行情进程，再有序切换执行服务。交易凭据、账户锁、订单核对、数据库和导入文件继续使用原账户和路径。行情中断期间，执行服务继续核对已受理的委托。行情采集的范围和恢复方式见 [行情监控](monitor.md)。

| 变更 | 部署动作 |
| --- | --- |
| 只更新公开采集或历史读取实现 | 只重启行情服务。安装器用执行账户访问行情套接字，核对实际进程和目标程序摘要。失败时恢复上一版行情服务，控制面和执行进程继续运行 |
| 只更新页面或控制面 | 沿用页面重载或控制面重启，行情进程继续采集 |
| 更新执行面，或改动多个组件共用的运行代码 | 重启实际受影响的组件，分别核验生效的程序和配置 |

`executor`、`control`、`market` 分别指向对应进程使用的发行目录，安装器清理旧包时保留这些目录。`current` 记录页面展示的已装版本。行情服务使用独立账户，通过 `/run/trading-platform-market/market.sock` 向执行服务提供公开行情。套接字权限为 0660，运行目录权限为 2750，专用组为 `trading-platform-market-ipc`。行情进程无法访问执行套接字、交易配置、数据目录以及两个助手的交接目录。

公开联网沿用 `/etc/trading-platform/environment` 里的代理配置。`PERPETUAL_COIN_IDS` 和 `COINGECKO_DEMO_API_KEY` 仍可在该文件设置。执行一键安装后，安装器把允许的配置写到 root 所有、权限 0600 的 `/opt/trading-platform/market.env`，systemd 在启动行情进程前载入。只改这两项时仅重启行情服务。交易账户密钥和页面更新凭据由各自的服务保管。

回退时用本版或更新的安装脚本执行 `sudo bash install.sh --version v0.66.0`。安装器停用并移除行情单元，由执行进程接回采集，对冲腿本地追价、Ondo 批量撤单和已有订单继续由该版本管理。Ubuntu CI 用 v0.66.0、v0.64.0 和 v0.63.0 的正式包验证双进程、单进程版本的往返切换。回到 v0.63.0 时，安装器先释放页面端口，再启动单进程服务。

真实 systemd 验收给四个故意启动失败的候选组件各留 8 秒，并核对相应服务日志中的预期异常。CI 按包摘要限定这个时限，正常组件、回退到好版本及正式安装都使用完整的 90 秒健康检查窗口。

## v0.64.0 控制面和执行面独立更新（R3）

从 v0.63.0 的单进程升级时，安装器做一次有序切换。之后，页面资源和发布版本可以独立切换，控制面可以单独重启。浏览器重新连接期间，执行器继续处理已受理的两腿任务、划转、ADL 和行情采集。

`trading-platform.service` 保留执行器、交易凭据、账户锁、写入租约和数据库。新的 `trading-platform-control.service` 接受浏览器连接，提供静态页面和在线更新，并经本机套接字转发交易 API。执行器继续验证原有会话、Host 和写请求。控制面只转发一次交易请求，丢失应答时按原请求编号核对。

安装器分别核对组件、配置与单元，保留运行进程引用的发布目录。控制面单独升级失败时恢复上一版页面和控制面。涉及执行面变更时沿用有序停机、健康检查和回退。首次升级请用页面「系统更新」或重新下载的一键安装脚本。回到单进程用 v0.64.0 的安装器执行 `sudo bash install.sh --version v0.63.0`，先释放浏览器端口再启动旧服务。首次迁移与迁回之间均只有一个交易写者。本期行情采集与实时交易继续在执行面内运行。

| 发布内容 | 安装器的动作 |
| --- | --- |
| 页面资源或版本信息 | 切换 `current`，通知原控制进程校验并载入新页面。上一份页面引用的哈希资源在该进程中再保留一版 |
| 控制面程序或控制单元 | 重启控制面。原会话和浏览器端口仍由同一套规则校验，账户推送、交易和巡检心跳继续 |
| 执行程序、运行依赖或执行配置 | 有序重启执行面。按账户锁和数据库租约获取写入权，按已有记录恢复任务。控制面只在自己的程序、单元或监听设置也变化时重启 |

正式包记录两个组件的内容摘要。`executor` 和 `control` 各自指向实际使用的程序目录，`current` 指向安装的发行版。控制面启动或重载时先完整读取并校验页面，再一次换入新资源和版本信息。执行器在每个套接字请求上核对目标执行组件的摘要。交易写入丢失应答或组件错配时，代理结束该连接，浏览器沿用原请求号核对。控制面退出后，执行器继续持有租约。

两个 systemd 单元分别使用 `trading-platform` 和 `trading-platform-control` 系统账户，通过专组访问执行器套接字。控制面使用独立的监听配置与更新目录 `/var/lib/trading-platform-update`，工作台导入沿用执行账户的 `/var/lib/trading-platform-import`。root 更新助手核对请求文件的 UID。首次从旧页面在线升级时，执行面向已登录的更新页提供旧助手的最终回执，浏览器可跟踪原更新请求。

命令行安装指定 `TP_UPDATE_DIR` 时，父目录须由 root 管理、组和其他人不可写，同时让控制账户拥有通往该目录的遍历权限。默认路径满足这些条件。

部署探针经真实回环端口检查 `/api/ready`，核对控制进程、已载入的发行目录、执行组件和双方监听设置。预热中的执行器可以报告未就绪。执行器不可达时，公开接口只返回 HTTP 503 和 `{"ready":false}`。安装器另在私有套接字核对执行器实际读入的配置。因此页面导入已使配置生效时，后续纯页面发布可以保留这一代执行进程。安装日志记录每个组件的实际动作。模拟验收见 [双进程连续性测试](../test/control-continuity.test.ts)。

拆分后的导入和更新队列由 systemd `PathExists` 监听。助手原子取走请求后再校验，处理期间收到的新请求留待下一次取走。误投到请求路径的目录留在同一交接目录隔离，后续请求可以继续处理。

权限、迁移和交易连续性的验收记录见 [控制面与交易执行面独立更新](reviews/2026-11-18-control-execution.md)。

## 1. v0.51.0 单进程版本的原始方案（R3）

**用户可见行为**

- 侧栏「系统」组多一个「系统更新」按钮，下方小字显示状态（已是最新、发现新版本、检查失败、正在更新、待启用）；有新版本时按钮高亮。
- 点开是对话框：当前版本 → 最新正式版、该版本的更新说明、上次检查时间；「检查更新」手动查一次；「查看更新」→ 确认区说明会重启服务 → 「确认更新到 vX」。
- 更新期间对话框显示进度（安装脚本最近的输出行）；服务重启时页面会断开几十秒，恢复后自动读取结果；成功后自动刷新页面载入新版本，失败时显示失败原因和安装脚本最后几行输出（是否已自动回退到原版本由 `install.sh` 输出说明）。
- 只能升级到比已装版本新的正式版，不能在页面降级；回退仍用命令行 `--version`。

**怎么做**

- 版本检查在服务进程里：每 30 分钟（启动后约 1 分钟第一次）读 GitHub `repos/hxx344/trading-platform/releases/latest`，取版本号、标题、更新说明、发布时间；v0.52.1 起两次之间每分钟探测一次发布页的跳转，发现新标签立即读一次（第 3 节）。手动检查最短间隔 60 秒；GitHub 返回限流时按它给的恢复时间暂停，手动检查也不绕过；其他失败按 1、2、4、8、15 分钟退避。走服务已有的代理设置（`NODE_USE_ENV_PROXY`）。
- 只支持默认安装路径（`/opt/trading-platform` 等）：助手执行的 `install.sh` 不带 `TP_APP_DIR` 之类的自定义路径变量。
- 「确认更新」：服务在页面导入用的交接目录（`/var/lib/trading-platform-import`，root 所有、服务组可写）写一个 `update-request.json`（只有请求编号、目标版本、时间）。新增 systemd 单元 `trading-platform-update.path` 监视这个文件，触发 root 单次服务 `trading-platform-update.service`。
- 更新助手（`src/service/update-helper.ts`，root）：只接受服务账户写的、2 分钟内的、格式为 `vX.Y.Z` 且比已装版本新的请求；用 curl 下载该版本的 `SHA256SUMS` 与 `install.sh`，核对 `install.sh` 的 SHA-256 后执行 `bash install.sh --version vX.Y.Z`；输出最近 40 行与阶段写进 `update-result.json`（服务账户可读），结束时写成功或失败。`install.sh` 本身照旧做程序包校验、配置检查、重启、90 秒健康检查和失败回退。
- 与导入、手动安装互斥：`install.sh` 持安装锁，另一个安装或导入在跑时本次更新失败并说明原因，不排队。
- 交接目录、服务单元、配置格式都不变；`install.sh` 只把新的两个单元加进已有的「页面助手单元」循环（渲染、安装、开机启用 `.path`）。

**影响面**

- 新增 root 执行路径：页面请求 → root 运行从 GitHub 下载的 `install.sh`。信任边界与手工一键部署相同：靠 TLS 与 GitHub 账号、Release 附件的完整性；`SHA256SUMS` 与 `install.sh` 同源，核对它只防下载不完整或混用不同版本的文件，不证明来源。残余风险（登记）：Release 附件被替换后，页面一点就会以 root 执行它，与手工执行一键部署命令相同。请求里只有版本号，经正则与“比已装版本新”两道检查，不能传任意参数、地址或降级。能发请求的只有已登录页面（POST 照旧要 `x-pa-executor` 头与会话）。
- 更新会重启服务：与手工执行 `install.sh` 相同，划转与 ADL 循环停几十秒，执行中的任务按已有恢复逻辑续上；确认区写明这一点。
- 服务进程多一个对 api.github.com 的只读请求（每 30 分钟一次），不带凭据；v0.52.1 起另有每分钟一次对 github.com 发布页的 HEAD 请求，同样不带凭据。
- 不碰下单、划转、ADL、凭据、数据库结构与配置格式。

**失败时与回滚**

- 版本检查失败：页面显示原因，不允许开始更新，交易不受影响。
- 更新失败：`install.sh` 在新版本启动不过时自动回退并确认旧版本运行；助手把结果和输出尾部写给页面。助手本身被 systemd 超时（30 分钟）或中断时，`ExecStopPost` 把未结束的结果标为“已中断”。
- 回滚本功能：`sudo bash install.sh --version v0.50.0`（README 回退表 v0.51.0 一行）。旧版本的 `install.sh` 不认识更新单元，不会删掉它们；残留的 `trading-platform-update.path` 无人写请求，不会触发。要清掉就 `sudo systemctl disable --now trading-platform-update.path` 并删除 `/etc/systemd/system/trading-platform-update.{path,service}`。

**本次不做（登记）**

- 工作台的 GitHub Token 配置（每分钟发现新版本改用不占 API 额度的发布页跳转，见第 3 节）、更新方式（源码 / CI 包）选择、事件流推送、下载进度条、新版本弹窗提醒、各阶段耗时：本服务只有一个程序包、更新由 `install.sh` 一次完成，页面每 2 秒读一次结果即可。
- 页面降级与选择任意版本。
- 首次启用：已装 v0.50.0 及更早版本的服务器上没有更新单元，需要在服务器上手工执行一次一键部署命令，之后才能在页面更新（页面在这种情况下显示“待启用”）。

## 2. 实际做法（v0.51.0）

**服务（`src/service/update.ts`，以服务账户运行）**

- `readInstalledVersion()` 读程序目录的 `VERSION`（`vX.Y.Z <提交>`，打包时写入）；开发检出没有它时取 `package.json`，标为非程序包，页面不允许更新。读不出版本号时只让在线更新不可用，不影响启动。
- `createUpdates()`：`tick()` 由后台循环每 15 秒调用一次，是否真的去 GitHub 由它按 30 分钟周期、首检 60 秒、退避和限流时间决定（两次之间的每分钟探测见第 3 节）；`check()` 是手动检查（60 秒内第二次返回 429 `update_check_wait`，限流期间返回 429 `update_rate_limited`）；`abort()` 在服务停止时中止进行中的请求。请求带 20 秒超时、只认 1 MB 以内的应答、链接只认本仓库的 Release 页。
- `apply({ version })` 依次拒绝：字段不对（400）、版本格式不对（400 `update_version`）、没有交接目录或没有就绪标记（409 `update_disabled`）、不是最近一次检查到的最新版（409 `update_changed`）、上次检查失败（409 `update_check_failed`）、不比已装版本新（409 `update_current`）、交接目录读不了（503）、有未取走的请求或运行中的更新（409 `update_busy`）。通过后以临时文件加改名写 `update-request.json`（600）。另外本机不是程序包安装时拒绝（409 `update_unpackaged`）。GitHub 应答边读边数，超过 1 MB 即中止；限流的恢复时间最多取 1 小时后。
- 助手先删请求文件、再写第一份“进行中”结果。服务记住自己最后写出的请求，请求文件不在、结果还没回答它（结果的 `id` 相同，或写在它之后的 `id` 为空的失败）时，2 分钟内仍按“等待处理”报告，页面不会在这段空档里丢掉盯住的任务（审查第 2 轮 P3）。服务重启后不再记得，只影响这段空档。
- 就绪标记 `<程序目录>/.update-helper`（`/opt/trading-platform/.update-helper`，root 所有、服务只读）由 `install.sh` 在更新 `.path` 启用并运行后写入，启用失败或所装版本没有更新助手时删掉；服务用 `updateReadyFile()` 从自己所在的 `releases/<包>/` 往上找到它，页面据此显示“待启用”。标记不放交接目录：那里服务账户可写，root 按路径写入会跟随服务放的符号链接（审查 P0）。

**HTTP（`src/http.ts`）**：`GET /api/update` 读状态，`POST /api/update/check`（空对象）手动检查，`POST /api/update/apply`（`{ version }`）确认更新；与其他接口一样要登录会话，POST 要 `x-pa-executor` 头；服务没接更新时三者 404。

**root 助手（`src/service/update-helper.ts`，`trading-platform-update.service` 启动）**

- 启动先把上次遗留的“进行中”结果标为中断（`--recover` 也由 `ExecStopPost` 调用，助手超时或被停止时同样处理）。
- 取请求：文件须为普通文件、单链接、属服务账户，否则删掉并写失败结果；取走即删除。请求超过 2 分钟、版本格式不对、本机不是程序包安装、版本不比已装的新，都写失败结果并说明原因，不下载。
- 下载 `releases/download/<版本>/SHA256SUMS` 与 `install.sh` 到临时目录（curl 只走 https、TLS 1.2 以上、重试 3 次），核对 `install.sh` 的 SHA-256 后以 `bash install.sh --version <版本>` 执行；输出去掉颜色控制符、每行最多 300 字、保留最近 40 行，有变化时每 2 秒、否则每 20 秒写一次 `update-result.json`（改归服务账户，600）。
- 退出码为 0 且 `current/VERSION` 已是目标版本才算成功；否则取输出里最后一条“安装失败：”（没有时取最后一行）作为原因，附当前版本。

**部署**：新单元 `deploy/trading-platform-update.path`（`PathChanged=@IMPORT_DIR@/update-request.json`）与 `deploy/trading-platform-update.service`（`Type=oneshot`、`TimeoutStartSec=1800`、`TimeoutStopSec=300`（超时停止时 `install.sh` 正在健康检查或回退，给它做完的时间；服务端把运行超过 2160 秒的结果算中断）、`PrivateTmp=yes`、读 `/etc/trading-platform/environment` 的代理设置）。`install.sh` 把它们并入导入助手的单元循环（`HELPER_UNITS`：渲染、安装、变更判断与 daemon-reload），`arm_path` 启用并启动两个 `.path`；所装版本带 `update-helper.ts` 且更新 `.path` 启用成功时写就绪标记。`package.sh` 把两个模板放进程序包。服务单元与命令行参数不变（沿用 `--import-dir`）。

**助手单元的命令行参数只增不改**：`install.sh` 回退版本时只还原服务单元，助手单元留在较新版本；助手以非严格模式解析参数、忽略不认识的，旧助手在新单元下照样工作。改参数含义或删参数要另想办法（例如回退时连助手单元一起还原）。

**页面**：见 [frontend.md](frontend.md)《系统更新（v0.51.0）》。

**测试**：`test/update.test.ts`（版本比较与更新说明、检查周期与退避、限流、确认更新的各项拒绝与请求文件、助手的成功、校验不符、下载失败、安装失败、过期与不更新的请求、非服务账户的请求、中断恢复、HTTP 路由的登录与请求标记）；`test/update-view.test.ts`（页面文字与能否开始更新）；`deploy/test-install.sh` 第 1 部分检查两个更新单元的路径已填好、测试模式不写就绪标记，并用替身 `systemctl`（`TP_TEST_ARM=1`）走启用路径：标记写在程序目录且为 644、交接目录里没有；更新 `.path` 启用失败时删掉标记且安装照常成功；装没有更新助手的版本时删掉标记、保留单元。

**未在本机验证**：systemd 真正触发 `.path`、root 下载 GitHub Release 并执行 `install.sh`、重启后页面自动刷新（本机没有 root 与 systemd 权限），首次在服务器上更新时实测并回填 [live-results.md](live-results.md)。

## 3. 每分钟发现新版本（v0.52.1，R2）

**要改变的行为**：新版本发布后，服务约 1 分钟内发现（原来最长 30 分钟），页面侧栏按原有的每分钟读取显示出来，合计最长 2 分钟多一点（后台循环每 15 秒看一次是否到点，探测实际间隔 60–75 秒）。安装仍要在页面确认，服务不会自己更新。

**为什么不直接每分钟读 API、也不加 Token**：不带 Token 的 GitHub API 每个出口 IP 每小时只有 60 次额度，每分钟读一次正好用完，手动检查或同一出口的别的程序再读就会被限流。工作台用 Token 把额度提到每小时 5000 次；本服务要这么做就得多一份凭据（保存、页面填写、导入），属于 R3。改用发布页的跳转就不占 API 额度，也不需要凭据：`https://github.com/hxx344/trading-platform/releases/latest` 应答 302，`Location` 是最新正式版的标签页（`…/releases/tag/vX.Y.Z`，与 API 的 latest 同一口径，不含预发布与草稿）。

**做法（`src/service/update.ts` 的 `probe()`）**

- `tick()` 里，API 检查未到期、且距上次探测或上次成功的 API 检查满 60 秒时发一次 `HEAD`（不跟随跳转，20 秒超时，服务停止时中止），只认 3xx 且 `Location` 以本仓库的 `releases/tag/` 开头、标签为 `vX.Y.Z` 的应答。
- 标签与上次从 API 读到的最新版相同：上次 API 检查成功时把「上次检查」时间更新为现在，否则什么都不改。
- 标签不同（或还没读到过最新版）：把 API 检查提前到现在，同一轮 `tick()` 里就读，版本号、更新说明等仍只来自 API，页面与确认更新的规则都不变。两种情况不提前：上一次 API 检查失败（按原有的退避重试），或距上次由探测提前的检查不足 5 分钟（发布页与 API 长时间不一致时，每小时最多多读 12 次）。GitHub 限流期间探测照常，但 API 要等到恢复时间。
- 探测失败（连不上、不是跳转、标签不合规）不改检查结果，也不在页面显示：只在第一次失败时写一行日志，恢复时再写一行；期间仍有每 30 分钟的 API 检查。
- 每 30 分钟的 API 检查保留：更新说明被修改、探测长期失败时靠它兜底。

**影响面**：只多一个出站只读请求；不碰更新请求、root 助手、安装脚本、配置与数据。请求量每天 1440 次，对象是 github.com 的网页而非 API。

**失败时与回滚**：探测失败时退回原来的 30 分钟一次。回滚版本 v0.52.0（`sudo bash install.sh --version v0.52.0`，不用改配置）。

**测试**：`test/update.test.ts` 新增四项（标签没变与变了、服务停止时探测静默结束、发布页与 API 不一致时的 5 分钟上限、探测失败的日志与退避期间不提前），并改了限流一项（限流期间只探测、不读 API）。

**实测**：本机用真实 GitHub 走了一遍（临时脚本直接调 `createUpdates()`，时钟每次拨快 1 分钟）：一次 API 检查读到 v0.52.0，之后三次探测里一次连接超时（记了失败日志，检查结果不变）、两次 302 到 v0.52.0 的标签页（记了恢复日志，「上次检查」时间前进），全程没有多余的 API 请求。没验证的：服务器上经代理的探测、真实发布后 1 分钟内发现，待下次发布时确认。

## 4. 页面在后台时跟进更新、别处发起的更新（v0.70.2，R2）

**问题**：页面靠读取 `GET /api/update` 得知自己跟着的更新已成功，再刷新页面载入新版本。共享读取层 `web/src/live-resource.ts` 在标签页隐藏时暂停全部读取，所以更新期间页面若在后台，就一直停在「正在更新」，回到前台才补读并刷新。另外，页面只在看到自己提交的、或亲眼看到运行的任务成功后才刷新；别的页面或设备发起的更新（包括只换页面资源、很快完成的更新）在本页隐藏或没轮到读取时结束，本页就一直运行旧页面。

**做法**

- `live-resource.ts` 的每个订阅者多一个 `background` 开关（`useLiveResource(..., { background })`，变化时只调整本订阅者）。条目里有任一订阅者打开时，页面隐藏也照常轮询；离线仍暂停。打开时立即补读一次并恢复轮询（加入已暂停的共享条目时同样）；关闭，或打开它的订阅者离开后，隐藏页面的条目随即暂停。其它读取不受影响。
- 「系统更新」在本页跟着一次更新时打开后台读取（`readsInBackground()`：盯住的任务未结束、请求等待取走或任务运行中、确认请求在途或结果未知；以及还没读到载入版本时，使在后台打开的标签页也先读一次），按原有每 2 秒读取；成功后照常 1.5 秒后刷新。浏览器会节流后台计时器（隐藏 5 分钟以上的标签页可能一分钟才读一次），刷新可能相应推迟，但不再等回到前台。
- 页面载入后第一次读到的服务版本记为载入版本。之后读到的 `current.version` 与它不同、且没有更新在进行（等待取走或运行中且未超时）时，同样显示「更新已完成，正在刷新页面」并刷新（`reloading()`）。更新进行中等结果，避免安装脚本回退前载入半途的版本。刷新后的页面以新的第一次读取为准（`nextLoaded()`），不会反复刷新。页面在后台且没有跟着的更新时仍不读取，回到前台第一次读取就会刷新。载入版本取自第一次读取而非页面资源本身：页面资源载入到第一次读取之间（通常不到一秒）完成的更新仍会漏掉，要在页面资源里写入版本才能消除，本次不做。

**影响面**：只改页面读取层与「系统更新」按钮；不碰服务端、更新助手和安装脚本。其它页面的读取行为不变（没有订阅者打开 `background`）。

**失败时与回滚**：后台读取出错时与前台一样保留上次结果、按间隔重试；距上次成功读取（或页面载入）满 10 分钟仍读不到时停止后台读取（`BACKGROUND_SILENCE_MS`），回到前台再按前台规则继续。回滚版本 v0.70.1（`sudo bash install.sh --version v0.70.1`，不用改配置）。

**测试**：`web/test/live-resource.test.mjs`（隐藏时普通订阅暂停、后台订阅照常轮询且离线暂停、隐藏时开关后台读取、打开它的订阅者离开后暂停、在途读取、401、读取中关闭、加入已暂停的共享条目、暂停时保留错误，以及与 `readsInBackground()` 串联的停读与恢复）；`test/update-view.test.ts` 新增版本变化刷新、后台读取条件、10 分钟停读与载入版本四项。

**未在本机验证**：真实浏览器后台标签页里的节流间隔与服务器上的真实更新，首次在服务器上更新时实测并回填 [live-results.md](live-results.md)。
