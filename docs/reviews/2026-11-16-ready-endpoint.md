# 免登录就绪接口 `GET /api/ready`（R3）审查记录

- 日期：2026-11-16
- 范围：`src/http.ts`（新增一条路由与 `ready` 选项）、`src/runtime.ts`（`READY_STALE_MS`、`loopsReady`、把判定交给 HTTP 服务；`loopStatus` 增加单调时钟字段 `okTick`，`/api/status` 不输出它）、`test/ready.test.ts`、`test/service.test.ts`（真实入口上补一条断言）、`README.md`、`docs/frontend.md`、`docs/executor.md`。
- 等级：R3（鉴权边界：第一次有 `/api/` 路径不经登录检查）。

## 变更前对齐

- 用户可见行为：`GET /api/ready` 不登录可读。就绪返回 200 `{"ready":true}`，否则 503 `{"ready":false}`。用途是让另一台服务器上的巡检（工作台的 main-watch）判断本服务是否正常，原来只能探测登录页或端口。
- 判定：没在停止、持有写入租约、每个被跟踪的循环最近 180 秒内完成过一轮（从未完成过一轮算未就绪）。循环就是「运行状态」页已有的那几个，不新增采集；时限按单调时钟算，不受系统时间跳变影响。
- 影响面：
  - 只放开这一个路径、只放开 GET；Host 头检查在它之前，其余路径的登录检查不变。
  - 应答只有一个布尔值，不含账户、余额、配置、版本、未就绪原因；不发 cookie，不读请求体，不触发任何外部请求或写库。
  - 监听地址不变（`127.0.0.1` 与 `config.host`），能连到端口的人原本就能看到登录页，现在多知道“服务是否就绪”。
  - 划转、ADL、下单、凭据、配置格式、数据库都不碰。
- 失败时与回滚：接口判定出错只影响巡检告警（误报或漏报），不影响交易。回滚 `sudo bash install.sh --version v0.45.0`，不用改配置和数据；回滚后巡检目标须改回 `tcp://`（设了登录密码时也可用 `/login`），否则会持续告警。
- 本次不做：
  - 「运行状态」页不显示就绪结论（页面已有各循环的最近成功时刻）。
  - 原油、期权、行情监控、资产等模块的后台循环没有进入 `loopStatus`，不参与判定。
  - 不判断交易所是否可达：划转、ADL、持仓读取单轮内部的交易所错误都被各自吞掉并记状态或事件，这一轮仍算完成，接口照样 200，这类故障仍靠服务自己的飞书告警。
  - 不改 `install.sh`，不代装 main-watch 的心跳推送端。

## 审查结论

两轮独立只读审查（每轮新开审查者，上下文与作者隔离），第 2 轮只复核第 1 轮的修复。P0、P1 两轮均为无。

已核实（第 1 轮）：新路由只在 `ready` 已提供、方法为 GET、路径恰为 `/api/ready` 时放开，排在 Host 检查之后；其余情况照旧走登录检查。路径变体（大小写、尾斜杠、编码、重复斜杠、`;x`）与 HEAD / OPTIONS 都不放开。应答只有一个布尔值，响应头没有 CORS，不发 cookie、不读请求体、不写日志，不影响登录限速与会话；`ready()` 抛错时由统一出口回 500，不带细节。两个入口都先取得租约再进运行循环，`loopStatus` 在开始监听前已登记。

## 已运行

本机为 Windows，Node v24.22.1。

- `pnpm check`：通过（第 2 轮 P3 修复后重跑）。
- `pnpm build:web`：通过（第 1 轮修复前运行；之后没有改页面）。
- `node --test test/ready.test.ts test/runtime.test.ts`：5 项全部通过（第 2 轮 P3 修复后重跑）。第 2 轮审查者另外串行跑 6 次、16 路并发跑 1 次，都通过。
- 变异核对：从 `ready` 里去掉 `!stopping`，“停止中”用例失败；去掉 `!executor.retired`，“失去租约”用例失败；两处都已还原。
- `pnpm test` 全套（第 1 轮修复前运行）：本机有 60 项左右失败，都是依赖 Linux 的用例（600 权限、目录 fsync、抽象套接字等）。同一时间在未改动的基线上跑全套作对比，失败的用例集合相同，只多一项“采集器：未运行时写入 503…”（`test/monitor-perpetual-paper.test.ts`），单独重跑 3 次都通过，属负载下不稳定，与本改动无关。
- `test/service.test.ts` 里真实服务入口上的新断言在本机跑不到（该用例在 Windows 上因 `EPERM fsync` 失败，基线同样失败），以 PR 的 CI（Ubuntu）结果为准。
