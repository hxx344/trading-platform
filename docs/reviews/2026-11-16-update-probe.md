## 审查结论

一轮独立只读审查（审查者上下文与作者隔离，只给仓库、差异范围、`docs/code-review.md` 与待核查重点）。P0、P1、P2 均为无，P3 四条。

| 级别 | 问题 | 处理 |
| --- | --- | --- |
| P3 | `docs/update.md` 第 3 节链接的审查记录还不存在 | 即本文件 |
| P3 | 页面标题与探测无关，却在同一批改动里，文档与回退表没提 | 拆成单独提交（R1），提交信息与发布说明写明 |
| P3 | 测试断言「读过 API 后 1 分钟内不探测」只因 `probeAt` 的初始值成立：之后的 API 检查不重置 `probeAt`，检查完的下一轮就可能多探测一次（只多一个 HEAD，结果正确） | `run()` 成功时把 `probeAt` 设为 60 秒后，断言对每次成功的 API 检查都成立；文档同步 |
| P3 | 缺三条边界的测试：探测进行中服务停止、探测与手动检查并发、相对路径或大小写不同的 `Location` | 补了服务停止一项（挂起的探测在 `abort()` 后静默结束、不记日志）；另两条登记不补：审查已核对代码在这两种情况下正确，后果至多是多一次 API 检查或退回 30 分钟一次 |

审查另指出两处小出入，已改文档：探测实际间隔 60–75 秒（后台循环每 15 秒看一次），连同页面每 60 秒读取，合计最长 2 分钟多一点。

已核实无问题：

- 探测只在 API 检查未到期时发生，只会把 API 检查提前、不会推后；API 检查失败后（含限流）`failures > 0`，探测不提前，退避与限流绕不过去；发布页与 API 长时间不一致时每小时最多多读 12 次。
- 探测完成后读的是当时的 `latest`、`error`、`failures`（L091）；`checkedAt` 只在上次 API 检查成功且标签相同时刷新。
- 应答只认 3xx、`Location` 以本仓库的 `releases/tag/` 开头且剩余部分完全是 `vX.Y.Z`；探测到的标签从不写入状态，`apply()` 仍只认 API 读到的最新版。
- 超时、连接失败、服务停止都不会让异常逃出 `tick()`；日志只在首次失败与恢复时各一行；更新检查在独立的后台循环里，不拖住划转与 ADL。
- Node 24 的 `fetch` 在 `HEAD` 加 `redirect: 'manual'` 下返回 302、可读 `location`、`body` 为 null（审查者用本地服务实测）。
- 全仓库写着版本检查周期的只有 `docs/update.md` 与 README，均已更新；页面文案没有写周期。
